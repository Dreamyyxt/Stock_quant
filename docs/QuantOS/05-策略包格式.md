# QuantOS 2.0 · 策略包格式（B8 / B9 起含调度语义）

> 这份文档是写给**写策略的人**看的，不是写给维护内核的人看的。
> 目标：收集来的策略不改内核就能进平台，且进不来的时候能立刻知道为什么。

---

## 0. 一个策略包长什么样

一个 `.py` 文件，两样东西：

```python
MANIFEST = { ... }                 # 自述
def compute(frame, ctx): ...       # 计算
```

没有基类、没有装饰器、不 import 任何生产模块。直接复制
`research/strategy_packs/_template.strat.py` 改名就能写。

**唯一约定**：`compute` 返回信号列表，每个信号是三键 dict：

```python
return [{"symbol": "600000", "weight": "0.05", "reason": "20日动量入选"}]
```

| 键 | 类型 | 说明 |
|---|---|---|
| `symbol` | str | 标的代码 |
| `weight` | 数字 | **相对本策略配额**的目标权重，范围 `[-1, 1]` |
| `reason` | str | 必填。事后要能回答「系统为什么做这笔交易」（R-G02） |
| `score` | 数字 | 可选，只做展示，**不参与金额计算** |
| `direction` | -1/0/1 | 可选，兼容老策略；只给方向不给权重会被丢弃 |

`weight` 的语义值得再说一遍：策略说 `0.15`，而策略配额占 NAV 的 30%，
那这笔实际占 NAV 4.5%。**策略永远不该知道 NAV 是多少** —— 知道了就会开始
算「我有 10 万，所以买 300 股」，仓位就脱离了资金管理。

## 1. MANIFEST 的每个字段

```python
MANIFEST = {
    "strategy_id": "ashare_ew20",   # 唯一标识，之后不能改（改了历史盈亏接不上）
    "version": "v1",                # 代码变了版本要变，否则指纹对不上会被拒
    "venue": "TIGER",               # 必须与行情 frame 的 venue 一致
    "kind": "rebalance",            # rebalance / signal（见下面的「调度语义」）
    "rebalance_days": 20,           # 多久调一次（日频 1 / 周频 5 / 月频 20）
    "warmup_bars": 25,              # 最少要多少根 bar 才允许计算
    "params": [                     # 可调参数，全部要声明
        {"name": "top_n", "kind": "int", "low": 1, "high": 100, "default": 20},
        {"name": "weight", "kind": "float", "low": 0.001, "high": 0.2},
    ],
    "author": "human:owner",
    "description": "中证800 等权 20 日再平衡",
}
```

`params` 的规则是硬的：
- **没声明的键传进来 → 报错**。不是忽略。代价是用户把 `lookback` 拼成
  `lookbak`，跑一年才发现参数从来没生效过。
- **`required=False` 必须给 `default`**。缺值又没默认值，等于必填，别绕。
- `low` / `high` 是硬边界，越界报错。
- `kind` 决定类型：`float` 走 `Decimal`（不是 float，避免 0.1+0.2 那类误差进策略）。

### 调度语义（B9 起 `rebalance_days` 真的被读了）

| 字段 | 谁在读 | 语义 |
|---|---|---|
| `kind="rebalance"` | `schedule.RebalanceSpec.due_on()` | 只有 `anchor + k × rebalance_days` 那些**交易日**才调仓 |
| `kind="signal"` | 同上 | 每个交易日都可以给信号，动不动的判断在策略自己 |
| `rebalance_days` | 同上 | **交易日**数，不是自然日。20 个自然日里永远混进 4-6 个周末 |

`anchor`（第一次调仓的交易日）**不在 manifest 里** —— 它是运维配置，落在
`state/quantos/schedule.json`。理由：manifest 是策略的属性，anchor 是"这台机器从哪天开始跑它"
的属性。同一份代码在两台机器上可以有不同的 anchor。

周期永远从 anchor 算。这意味着**漏跑只是少跑一次，不会让之后每一次都晚一天**。
另外 `signal_day()` 规定当日必须在「收盘 + 结算延迟」之后才算，否则退回上一个交易日 ——
14:00 拿到的那个价格也叫 close，但它不是 15:00 那个。

## 2. compute 能拿到什么

```python
def compute(frame, ctx):
    frame.venue            # 场所
    frame.as_of            # 行情截止时间（带时区）
    frame.symbols()        # 本次可见的标的
    frame.require("600000", 21)   # 最近 21 根；不足直接抛 FrameError
    frame.latest_prices()  # {symbol: 最后价格}

    ctx.params             # 已校验的参数（Decimal / int / bool / str）
    ctx.positions          # 本策略当前持仓 {symbol: 数量}
    ctx.as_of              # 同 frame.as_of
```

**没有 `nav`，没有账户，没有下单接口。** 这是刻意的（R-A06）。

`require()` 的语义是硬门槛：要 21 根就必须要到 21 根，少一根也不许用现有数据凑。
半截窗口算出来的指标不会报错，只会悄悄偏 —— 这是最危险的一类错误。

## 3. 不许做的事（AST 体检会当场拒）

| 禁止 | 原因 |
|---|---|
| `import os` / `sys` / `subprocess` / `socket` / `requests` / `urllib` | 策略不该碰文件、网络、进程 |
| `open()` / `exec()` / `eval()` / `compile()` / `__import__()` / `input()` | 同上，且是逃逸入口 |
| `globals()` / `locals()` / `vars()` / `setattr()` / `delattr()` | 绕过静态检查的常见手法 |
| 访问 `__dunder__` 属性（如 `x.__class__.__bases__`） | 经典沙箱逃逸路径 |
| 顶层写 `print(...)` / 调函数 / `for` / `if` | 导入即执行会把调度器搞乱 |

允许的 import 白名单：`math` `statistics` `decimal` `fractions` `operator`
`datetime` `typing` `dataclasses` `collections` `itertools` `functools`
`enum` `string` `re`，以及**唯一一个**生产模块 `quantos_core.strategy_api`
（纯数据契约，无 IO、无状态）。用它的场景只有 `from quantos_core.strategy_api
import SignalOut`，而更推荐直接返回 dict。

> **诚实说明**：AST 体检是**门槛，不是沙箱**。它挡得住无意的越界，
> 挡不住精心构造的逃逸。真正的隔离要独立进程 + 无网络 + 只读文件系统 + 资源限额，
> 那属于部署层（B10）。所以规则是：**只从你信任的来源导入策略包。**

## 4. 导入：一条命令

```bash
# 用真实 A 股日线干跑一遍
.venv/bin/python scripts/quantos_strategy_import.py \
    --pack research/strategy_packs/ashare_ew20.strat.py --set top_n=5

# 只要结论（批量导入 / CI 用）
.venv/bin/python scripts/quantos_strategy_import.py --pack x.strat.py --json
```

输出会给出：指纹（12 位 sha256）、解析后的参数、干跑信号条数与内容、告警。
**退出码 0 = 可以进 RESEARCH；1 = 体检不过；2 = 用法或数据问题。**

导入过程强制做五件事：

1. AST 体检
2. 源码指纹 `sha256(源码)[:12]` → 写进 `code_commit`
3. manifest 校验（字段、参数 schema、未知键）
4. **干跑一次**：真调 `compute()`，返回 `None` / 字符串 / 未知键的 dict / 抛异常，全部当场拒
5. 落成 **RESEARCH** 阶段实例

第 5 条没有开关。导入动作的语义就是"进研究区"；要上模拟盘走
`StrategyRegistry.promote()` 的准入检查（R-S03），那条路上有：
样本外回测、真实成本、模拟盘状态、异常订单测试、人工授权，五件材料缺一不可。

## 5. 从 RESEARCH 到 LIVE 要过什么

```
RESEARCH ──► BACKTEST ──► PAPER ──► LIVE
   导入        回测可复现    模拟盘    小额实盘
```

| 卡口 | 检查 |
|---|---|
| 任意跳级 | `IllegalStageTransition`（不能 RESEARCH 直跳 PAPER） |
| 进 PAPER | 必须有 `backtest_report_id` + `code_commit` + `data_version` + `cost_model_version` |
| 进 LIVE | 上面全有 + **人工授权**（自动化 actor 被拒）+ 模拟盘观察期已满 |
| 已 LIVE 的版本替换 | 必须先降回 PAPER —— 防「热换代码」 |
| 资金分配候选池 | 只收 PAPER / LIVE。RESEARCH 与 BACKTEST 导一万个也不会产生订单 |

最后一条是 B8 补上的一个真实漏洞：`tradable` 只看运行状态不看阶段，
于是一个刚导入的研究策略会带着配额被交进资金分配器。

## 6. 一个常被问的问题：为什么不能直接算金额？

因为「策略判断」和「这笔钱怎么给」是两个问题，混在一起之后：

- 两个策略各说自己要买 2 万，加起来可能超了总敞口，而谁也不知道对方要买；
- 风控想按 NAV 比例限制单笔金额时，发现订单里的数量已经是策略算好的绝对值；
- 回测时按 100 万本金算权重，实盘 10 万，策略参数全部要重调。

所以：**策略给权重，资金管理给额度，风控给上限，OMS 给数量。**
每一层只回答一个问题，出问题时才知道该查哪一层。
