# QuantOS 2.0 · 五服务边界与数据契约

> 对应需求 `R-G08`。本文定义 `Strategy Engine → Capital Allocator → Risk Engine → OMS/EMS → Portfolio Ledger`
> 的职责边界、字段级数据契约、状态机与错误语义。
> **本文是代码与测试的验收依据**：`quantos_core/` 下实现必须与本文逐字段一致。

---

## 0. 五条全局铁律

| 编号 | 铁律 | 违反后果 |
|---|---|---|
| G-1 | **单向依赖**：左侧服务不得 import 右侧服务的模块。策略永远不知道 OMS 存在。 | 回测/实盘行为分叉，无法事件回放 |
| G-2 | **金额用 `Decimal`，禁用 `float` 做累加** | 分币误差累积、对账永远不平 |
| G-3 | **所有事件带 `as_of`（数据时间）+ `ts`（产生时间）** | 陈旧数据参与决策，回测偷看未来 |
| G-4 | **幂等键由上游生成，重试复用同一键** | 超时重试造成重复下单（R-A08） |
| G-5 | **失败默认关闭（fail-closed）**：拿不到确定答案就不许新增风险 | 断网时继续开仓 |

## 1. 职责边界表

| 服务 | 唯一输入 | 唯一输出 | 明确**不**做的事 |
|---|---|---|---|
| Strategy Engine | 行情（带 `as_of`）+ 策略参数 | `Signal` / `StrategyIntent` | 不下单、不查持仓、不算可买数量、不做风控 |
| Capital Allocator | 各策略 `StrategyIntent` + NAV + 现有持仓/在途订单 + 波动率 | `TargetPosition`（净额）+ `StrategyAllocation` | 不判断信号好坏、不检查单笔风险、不接触 Broker |
| Risk Engine | `OrderIntent` + `RiskState` + 持仓 + 行情新鲜度 + 对账状态 | `RiskDecision` + 新的 `RiskState` | 不改订单数量（只 ALLOW / REJECT / 要求降规模）、不下单 |
| OMS/EMS | 已批准的 `OrderIntent` | `Order` 状态流 + `Fill` | 不做策略判断、不做资金分配、不猜订单状态 |
| Portfolio Ledger | `Fill` + 外部资金流 + 期末价格 | `Position`（含策略归属）+ `NAV` + 归因 + `ReconciliationReport` | 不读券商余额当真相、不参与下单决策 |

**为什么 Risk 不允许改单量**：一旦风控能"帮忙调小"，实际下单量就同时由风控和组合层决定，出问题无法归因。风控只能三选一：放行 / 拒绝 / 要求上游按指定上限重算。

## 2. 领域对象契约

### 2.1 Signal（策略信号，不可变）

| 字段 | 类型 | 说明 |
|---|---|---|
| `signal_id` | str | 全局唯一，`{strategy_id}:{symbol}:{ts_epoch}` |
| `strategy_id` | str | 稳定标识，不含版本 |
| `strategy_version` | str | 语义版本，如 `1.3.0` |
| `symbol` / `venue` | str | `BTC/USDT` / `OKX`；股票 `QQQ` / `TIGER` |
| `kind` | enum | `ENTER_LONG` `EXIT_LONG` `ENTER_SHORT` `EXIT_SHORT` |
| `strength` | Decimal | 0..1，策略内部指标 |
| `reason_code` | str | 机器可判定原因，如 `trend_following` `breakout_20d` |
| `as_of` | datetime(UTC) | **生成该信号所依据的行情时间** |
| `ts` | datetime(UTC) | 信号产生时间 |
| `expires_at` | datetime(UTC) | **过期后不得用于下单**（R-K01 信号过期） |

### 2.2 StrategyIntent（策略唯一合法出口，R-A06）

```json
{
  "intent_id": "crypto_trend_v1:v2.0.1:20261026T010000Z:BTCUSDT",
  "strategy_id": "crypto_trend_v1",
  "strategy_version": "2.0.1",
  "symbol": "BTC/USDT",
  "venue": "OKX",
  "target_weight": "0.15",
  "confidence": "0.82",
  "reason": "trend_following",
  "signal_ids": ["crypto_trend_v1:BTC/USDT:1792976400"],
  "as_of": "2026-10-26T00:59:00Z",
  "ts": "2026-10-26T01:00:00Z",
  "expires_at": "2026-10-26T05:00:00Z",
  "reduce_only_hint": false
}
```

契约要点：
- `target_weight` 是**相对该策略分配额度**的权重（`-1..1`），不是相对 NAV。策略不知道 NAV，否则策略就在做资金分配。
- `confidence` **只记录、只展示、不参与任何计算**（R-A06）。代码中 `confidence` 字段不允许出现在 `capital_allocator.py` 的算术表达式里。
- `reduce_only_hint` 仅建议，最终由 Risk Engine 权限级裁定。

### 2.3 StrategyAllocation（Capital Allocator 输出）

| 字段 | 类型 | 说明 |
|---|---|---|
| `strategy_id` | str | |
| `mode` | enum | `fixed_quota` / `vol_target`（第一版仅这两种，R-C03） |
| `quota_usd` | Decimal | 该策略可用名义额度 |
| `max_gross_weight` | Decimal | 相对 quota 的总敞口上限 |
| `vol_scalar` | Decimal | 波动率缩放系数（0..1] |
| `risk_budget_pct` | Decimal | 占基金风险预算比例 |
| `effective_capacity_usd` | Decimal | `quota_usd * vol_scalar`（派生，只读） |

### 2.4 TargetPosition（组合层净额结果，R-A07 落地）

```json
{
  "symbol": "BTC/USDT",
  "venue": "OKX",
  "per_strategy": { "crypto_trend_v1": "15000.0", "crypto_mr_v1": "-7500.0" },
  "net_target_notional": "7500.0",
  "current_notional": "3000.0",
  "inflight_notional": "0.0",
  "delta_notional": "4500.0",
  "net_target_qty": "0.0421",
  "delta_qty": "0.0253",
  "decision": "TRADE",
  "blocked_reason": null
}
```

契约要点：
- `per_strategy` **必须保留每个策略的归属**，否则无法按策略算盈亏（R-D05）与风险贡献（R-C04）。
- `inflight_notional` 必须从 OMS 的未成交订单读入，**净额计算必须扣掉在途**，否则同一意图在两次调度间被重复下单。
- `decision` ∈ `TRADE` / `NOOP` / `BLOCKED`。`BLOCKED` 必须给 `blocked_reason`（如 `min_notional` `stale_intent` `strategy_paused`）。

### 2.5 OrderIntent（唯一合法下单请求，R-K01 订单级入口）

| 字段 | 类型 | 说明 |
|---|---|---|
| `order_intent_id` | str | 本次决策唯一 ID |
| `client_order_id` | str | **稳定幂等键**，重试复用（G-4） |
| `account_id` / `venue` / `symbol` | str | |
| `side` | enum | `BUY` / `SELL` |
| `quantity` | Decimal | 基础单位数量（币为小数，股为整数） |
| `order_type` | enum | `LIMIT` / `MARKET`（默认 LIMIT） |
| `limit_price` | Decimal? | 限价单必填 |
| `notional` | Decimal | 名义金额（用于订单级风控） |
| `attribution` | dict | `{strategy_id: 分摊数量}`，供账本归属 |
| `reason_chain` | list[dict] | `[{intent_id, reason_code, confidence}]` |
| `reduce_only` | bool | 风控置为 REDUCE_ONLY 时强制 true |
| `as_of` / `ts` | datetime | |

`client_order_id` 生成规则（必须确定性，重试不变）：

```
{account_id}-{strategy_scope}-{symbol_slug}-{yyyymmdd}-{seq:04d}
例：TIGER-PAPER-crypto_trend_v1-BTCUSDT-20261026-0007
```

### 2.6 Order（OMS 状态机，R-A08）

**状态**：`CREATED` `SUBMITTED` `ACCEPTED` `PARTIALLY_FILLED` `FILLED` `PENDING_CANCEL` `CANCELLED` `REJECTED` `EXPIRED` `UNKNOWN`

**合法迁移表**（未列出的迁移一律 `IllegalTransition`，不允许"容忍"）：

| From | 允许的 To |
|---|---|
| CREATED | SUBMITTED, REJECTED |
| SUBMITTED | ACCEPTED, REJECTED, UNKNOWN, EXPIRED, PARTIALLY_FILLED, FILLED |
| ACCEPTED | PARTIALLY_FILLED, FILLED, PENDING_CANCEL, CANCELLED, EXPIRED, UNKNOWN |
| PARTIALLY_FILLED | PARTIALLY_FILLED, FILLED, PENDING_CANCEL, CANCELLED, EXPIRED, UNKNOWN |
| PENDING_CANCEL | CANCELLED, PARTIALLY_FILLED, FILLED, UNKNOWN |
| UNKNOWN | ACCEPTED, PARTIALLY_FILLED, FILLED, CANCELLED, REJECTED, EXPIRED |
| FILLED / CANCELLED / REJECTED / EXPIRED | （终态，无出边） |

**三条硬规则**：
1. **超时 ≠ 失败**。`SUBMITTED`/`ACCEPTED` 超时只能迁到 `UNKNOWN`，然后进入 `reconcile` 流程。**`UNKNOWN` 没有任何通往"重新提交"的边**。
2. **重复回报幂等**：同一 `venue_trade_id` 的 `Fill` 只入账一次；同一 `client_order_id` 已存在活动订单时，新的提交请求必须返回既有订单而不是新建。
3. **部分成交必须入账**：`PARTIALLY_FILLED` 的每次增量 `Fill` 独立记账，不允许等终态一次性记账（否则崩机丢成交）。
4. **成交回报即接受证据**（2026-10-26 补充）：`SUBMITTED` 允许直接迁到 `PARTIALLY_FILLED` / `FILLED`。理由是现实中 WS 可能漏掉 ack 而先到 fill（快速成交、断线重连补发）。若强制要求先 `ACCEPTED`，会把正常成交判为非法迁移而**丢失成交记录** —— 丢失成交比状态"跳步"危险得多。

### 2.7 Fill

| 字段 | 类型 | 说明 |
|---|---|---|
| `fill_id` | str | 本地唯一 |
| `order_id` / `client_order_id` | str | |
| `venue_trade_id` | str | 交易所成交 ID，用于幂等去重 |
| `quantity` / `price` | Decimal | |
| `fee` / `fee_currency` | Decimal / str | |
| `liquidity` | enum | `MAKER` / `TAKER`（决定费率回算） |
| `ts` | datetime | 成交时间 |

### 2.8 RiskDecision / RiskState

```json
{
  "decision_id": "rd-20261026-000123",
  "layer": "ORDER",
  "policy_key": "max_order_notional_pct",
  "verdict": "REJECT",
  "subject": {"type": "order_intent", "id": "oi-0007"},
  "inputs": {"order_notional_pct": "3.1", "limit": "2.0"},
  "reason": "order notional 3.1% of NAV exceeds max_order_notional_pct 2.0%",
  "ts": "2026-10-26T01:00:01Z"
}
```

`verdict` ∈ `ALLOW` / `REJECT` / `REDUCE_REQUIRED`（要求上游按给定上限重算）/ `PAUSE_STRATEGY` / `HALT_FUND`
`layer` ∈ `ORDER` / `STRATEGY` / `FUND`

`RiskState` 关键字段：`permission_level`（NORMAL/REDUCE_ONLY/HALTED）、`halted_reasons[]`、`strategy_status{strategy_id: ACTIVE/REDUCE_ONLY/PAUSED}`、`drawdown_pct`、`daily_pnl_pct`、`data_stale`、`reconciliation_broken_accounts[]`。

## 3. 权限级语义（R-K03 / R-K04）

| 权限级 | 允许 开仓 | 允许 减仓 | 允许 撤单 | 触发条件示例 |
|---|---|---|---|---|
| `NORMAL` | ✅ | ✅ | ✅ | 一切正常 |
| `REDUCE_ONLY` | ❌ | ✅ | ✅ | 策略超风险贡献、组合敞口超限、单个策略异常换手 |
| `HALTED` | ❌ | ❌（仅"受控减仓"通道） | ✅ | 回撤超阈值、资金不一致、行情陈旧、交易所异常 |

**HALTED 三种处置，按异常类型选择，禁止一律市价清仓**：

| 异常类型 | 处置 |
|---|---|
| 行情断连 / WebSocket 掉线 | 冻结新增订单 + 撤未成交委托；**持仓不动**（看不见价格时清仓是赌博） |
| 订单状态未知 | 冻结该标的 → 查询 → 对账；不撤不补 |
| 资金/持仓不一致 | 冻结该账户全部新增 + 人工排查 |
| 回撤超阈值 | 撤未成交 → 按流动性分批受控减仓（限价，不市价砸） |

## 4. 账本契约（R-D01 / R-D03 / R-D04）

### 4.1 会计科目（chart of accounts）

```
资产  cash:{account}:{ccy}          现金
      position:{venue}:{symbol}     持仓（按数量×市价计价）
      receivable:{ccy}              应收（T+1 未结算卖出款）
负债  payable:{ccy}                 应付（未结算买入款）
权益  equity:capital                外部投入本金（入金/出金，不进收益）
损益  pnl:trading                   价差收益（已实现+未实现）
      pnl:fee                       手续费（负）
      pnl:slippage                  滑点成本（相对决策价）
      pnl:funding                   资金费率（Crypto）
      pnl:fx                        汇率折算损益
```

**入金绝不计入 `pnl:*`**，只进 `equity:capital`（R-D03）。这是"收益率不被出入金扭曲"的唯一实现方式。

### 4.2 双分录示例（买入 0.1 BTC @ 60000，手续费 6 USDT）

| 科目 | 借 | 贷 |
|---|---|---|
| `position:OKX:BTC/USDT` | 6000 | |
| `cash:OKX:USDT` | | 6000 |
| `cash:OKX:USDT` | 6 | |
| `pnl:fee` | 6 | |

每笔 `LedgerEntry` 必须满足 `Σ借 = Σ贷`，否则拒绝入账（`UnbalancedEntry`）。这是对账永远平的根本保证。

### 4.3 NAV 与归因

```
NAV(base) = Σ 资产(base) - Σ 负债(base)
net_return = (NAV_end - NAV_begin - net_external_flow) / (NAV_begin + 加权外部流)
attribution = pnl:trading + pnl:fee + pnl:slippage + pnl:funding + pnl:fx   （必须恒等于净收益）
```

`attribution` 各项之和与净收益不等时 → 抛 `AttributionMismatch`，说明有未分类损益漏记，**不许四舍五入糊过去**。

### 4.4 对账（R-D04）

| 对账项 | 差异容忍 | 差异处理 |
|---|---|---|
| 现金 | 0（严格） | 账户置 `reconciliation_broken` → 禁新增 |
| 持仓数量 | 0（严格） | 同上 |
| 未成交订单集合 | 允许交易所侧多出"手工单"，但必须登记 | 报警，不阻断 |
| 成交记录 | 以 `venue_trade_id` 去重后必须完全一致 | 差异 → 阻断 |

`reconciliation_broken_accounts` 非空时，Risk Engine **强制**该账户 `HALTED`（R-K02 的 `position_mismatch_action: block_orders`）。

## 5. 时序：一次完整决策（含冲突与失败）

```
T0  行情 tick(as_of=T0) ──► Strategy Engine
T1  两策略分别产出 intent：
      trend:  target_weight +0.20 → 名义 +20000
      mr:     target_weight -0.08 → 名义  -8000
T2  Capital Allocator：
      quota(trend)=80000, quota(mr)=40000, vol_scalar 各 0.75
      → per_strategy{trend:+15000, mr:-6000}
      → net_target_notional = +9000
      读 OMS 在途 +2000 → delta = +7000
      → TargetPosition(decision=TRADE, delta_qty=0.0394)
T3  Risk Engine（订单级）：
      notional 7000 / NAV 105200 = 6.65% > max_order_notional_pct 2.0%
      → verdict = REDUCE_REQUIRED, cap = 2104
T4  Capital Allocator 重算（按 cap 缩放，不改原意图）
      → delta_notional = 2104, delta_qty = 0.0118
T5  OMS：client_order_id 固定，提交 → ACCEPTED
T6  Broker 回报 PARTIALLY_FILLED 0.006
      → Fill 入账（position↑, cash↓, fee↑）→ 更新持仓
T7  超时未终态 → 迁 UNKNOWN → 冻结该 symbol → 查交易所
      → 查到已 FILLED → 补录剩余 0.0058 的 Fill → 解冻
T8  Portfolio Ledger 日终对账
      → 现金/持仓/成交三项一致 → 解除冻结
      → 若不一致 → 账户 HALTED + 人工排查
```

**关键点**：T3 的 `REDUCE_REQUIRED` 不能让风控自己改单量，必须回到 T4 由 Capital Allocator 用原意图重算——这样"为什么下单 2104 而不是 7000"永远能追到 `decision_id` 与原始 `intent_id`。

## 附录 A · 事件类型契约（B1 补充）

回放器（`quantos_core/replay.py`）按 `seq` 顺序消费以下 11 类事件。新增事件类型时必须同步扩回放器，否则回放会**静默丢步骤**。

| 事件类型 | 关键 payload | 说明 |
|---|---|---|
| `deposit` / `withdraw` | `account_id, currency, amount, fx_to_base` | 进出金不进 pnl |
| `market_snapshot` | `venue, symbol, as_of, bid, ask, last, sequence` | 缺价字段留 `null`，禁止填 0 |
| `strategy_intent` | `strategy_adapter.intent_to_payload()` 全字段 | 策略唯一出口 |
| `cycle` | `now` | 触发一次「净额 → 风控 → 下单」；决策时间取自这里而非墙钟 |
| `order_ack` | `client_order_id` | SUBMITTED → ACCEPTED |
| `order_timeout` | `client_order_id` | → UNKNOWN 并冻结标的，**不重提** |
| `venue_status` | `client_order_id, venue_status, venue_filled_qty, venue_found` | 对账结果，UNKNOWN → 确定状态 |
| `fill` | `client_order_id, venue_trade_id, quantity, price, fee, quote_ccy` | 按 `venue_trade_id` 去重 |
| `permission` | `level, reason` | NORMAL / REDUCE_ONLY / HALTED |
| `strategy_state` | `strategy_id, state` | ACTIVE / REDUCE_ONLY / PAUSED |

**回放确定性要求**：`ReplayResult.digest` 只覆盖目标、决策、订单状态、账本、绩效 —— 刻意排除 `Order.history` 的时间戳（那里有 `utcnow()`）。任何新增字段若要进 digest，必须是可复现的。

## 附录 B · 落盘快照契约（T-202）

OMS 重启恢复必须同时读到**订单状态**和**原始意图**：

```
{"client_order_id": "...", "order_id": "...", "state": "SUBMITTED",
 "filled_qty": "0", "avg_fill_price": null,
 "intent": { ...OrderIntent 全字段，见 codec.intent_to_payload() }}
```

只存订单状态是不够的：恢复后要拿 `attribution` 做策略归属、拿 `reduce_only` 判断权限。缺了这两个字段，恢复出来的订单在风控眼里就是另一笔单。

## 附录 C · 运维 API 契约（B3 / T-301~T-303）

运维面是**只读为主 + 少量受控写**的内部接口，不是业务接口。它不参与交易链路，
宕机不影响策略、订单、风控（`OpsHttpServer` 与交易进程可分离部署）。

### C.1 传输与安全边界

| 项 | 约定 | 理由 |
|---|---|---|
| 监听地址 | **只允许 `127.0.0.1` / `::1`**，构造时传 `0.0.0.0` 直接抛异常 | 页面上有账户、持仓、策略列表，等于半个账户凭证 |
| 端口 | 默认 `8787` | — |
| 认证 | 写操作需 `X-Ops-Token` 头且与配置一致；读操作不校验 | 单机单人定位下的取舍，**不是安全方案** |
| CORS | 不发任何 `Access-Control-Allow-*` | 避免任意网页跨域读持仓 |
| 请求体上限 | `MAX_BODY_BYTES = 64 * 1024` | 防止误发大包把进程拖死 |
| 动作执行者 | `actor` **由 token 推导，绝不从请求体取** | 否则谁都能自称 `human:alice` 把自写策略放上实盘 |

### C.2 端点

| 方法 | 路径 | 返回 | 说明 |
|---|---|---|---|
| `GET` | `/` `/index.html` | HTML | 控制台页面（未配 `html_path` 时返回错误 JSON，不报 500） |
| `GET` | `/api/ops/health` | `{ok, ts, strategies, write_enabled}` | 存活探针 |
| `GET` | `/api/ops/snapshot` | `OpsSnapshot.to_dict()` | 指标快照，见 C.3 |
| `GET` | `/api/ops/strategies` | `{as_of, count, strategies[], inconsistencies[]}` | 策略实例 + 与审计的差异 |
| `GET` | `/api/ops/audit?limit=N` | `{as_of, count, digest, records[]}` | 默认 50 条，钳在 `1..500`，**倒序**返回 |
| `POST` | `/api/ops/actions` | `{ok, action, strategy, audit_seq}` 或 `{ok:false, error, error_type}` | 见 C.4 |

### C.3 指标快照结构

```json
{
  "as_of": "2026-10-26T11:20:31+00:00",
  "overall": "critical",
  "headline": "market · TIGER 最旧快照已 600.2s 未更新（另有 6 项）",
  "counts": {"ok": 9, "warn": 0, "critical": 7, "not_configured": 0},
  "root_causes": [{"component": "market", "key": "market.latency.TIGER", "detail": "…"}],
  "components": {"market": "critical", "orders": "critical", "portfolio": "ok"},
  "metrics": [{"key":"…","label":"…","value":…,"unit":"…",
               "severity":"ok|warn|critical|not_configured",
               "threshold":…,"detail":"…","source":"…","component":"…"}],
  "facts": {"portfolio.nav": 99996.45, "orders.total": 3}
}
```

**四条硬语义（改代码时不能破）**：

1. `severity` 只有四档，`not_configured` **不等于健康**。探针未接时必须报
   `not_configured`，`worst()` 会把它计入需关注。为了"全绿"把它改成 `ok` 等于
   把"没测"伪装成"测过且正常"。
2. 拿不到数字时 `value` 必须是 `null`，**禁止填 0**。0 是有效数值（0 笔失败订单是好消息），
   `null` 才是"不知道"。
3. `root_causes` 按严重度排序、只保留非 ok 项，`headline` 取第一条 —— 这样告警消息
   能直接说"哪个组件、什么现象"，不用人再去翻 `metrics` 数组。
4. `facts` 是给页面做数字比对的**未加工真值**（NAV、订单数等），与 `metrics` 里的
   展示值分离，避免"为了好看四舍五入"污染验收。

指标 `component` 取值固定为八个：`market` / `feed` / `strategy` / `execution` /
`orders` / `reconcile` / `risk` / `portfolio`。

### C.4 动作契约

请求体：`{"action": "...", "strategy_id": "...", "reason": "...", ...}`

| `action` | 额外字段 | 语义 |
|---|---|---|
| `pause` | — | 暂停该策略：**冻结自身存量，不清仓**，不参与新增净额 |
| `degrade` | — | 降为仅减仓：只允许减少自身敞口，不许反向、不许加仓 |
| `resume` | `live: bool` | 恢复运行；`live=true` 需再过 LIVE 闸门 |
| `set_canary` | `canary_weight` | 灰度权重，**真实缩放配额**，不是显示用 |
| `set_quota` | `quota_pct` | 直接设配额百分比 |
| `promote` | `to_stage` + `backtest_report_id` / `code_commit` / `data_version` / `cost_model_version` | 阶段晋级；进 `LIVE` 必须过三道闸 |

**错误语义**：被准入/风控拒绝是**正常业务结果**，返回 `200 + {ok:false, error_type}`，
不开 500。`error_type` 区分 `bad_request`（缺参数）/ `bad_argument`（参数不合法）/
`StrategyRegistryError` 子类（被闸门拒绝）。三种情况**都已在审计里留痕**，
`audit_seq` 指回那条记录。

**副作用**：动作成功后立刻 `registry.apply_to(risk_state)`。否则会出现
"页面显示已暂停、实际还在下单"这种最坏的不一致。

### C.5 页面数据源降级契约

`quantos/index.html` 的取数规则：

1. 先请求 `/api/ops/snapshot`；
2. 成功 → 实时模式，页面顶部标 `实时`，所有数字来自接口；
3. 失败 → **回退演示数据，并在顶部显式标 `演示数据`**；
4. **绝不静默混用**：不允许一部分数字来自接口、一部分来自常量而不做标注。

验收用 `scripts/quantos_ops_check.py` 做「接口 vs 进程内对象」逐项比对（6 项），
不使用页面数字作为验收依据 —— 页面只是渲染层。

## 附录 D · 实盘就绪契约（B4 / T-401~T-403）

B4 的契约不是"接口长什么样"，而是**"什么条件下才允许真钱出去、什么条件下账必须对得上"**。
这三份契约一旦被放宽，前面 B0~B3 做得再对也没有意义。

### D.1 三级实盘开关（T-401）

**三级各自独立，任一级不成立即拒单。** 没有"少一级就走纸面"的降级路径。

| 层级 | 武装接口 | 携带的上限 | 说明 |
|---|---|---|---|
| 账户级 | `arm_account(account_id, gross_cap_pct)` | 账户总敞口 % NAV | 「这个账户今天允许碰真钱吗」 |
| 策略级 | `arm_strategy(account_id, strategy_id, notional_cap)` | 该策略名义额度 | 「这个策略今天允许碰真钱吗」 |
| 单笔上限 | `set_order_cap(account_id, max_notional)` | 单笔绝对金额 | 「这一笔最多多大」；**无默认值** |

**三道显式确认**（`Confirmation{actor, reason, echo}`）：

| 字段 | 约束 | 挡的是什么 |
|---|---|---|
| `actor` | 必须以 `human:` 开头 | AI / 脚本把策略自己放上实盘 |
| `reason` | ≥ 6 字 | 「嗯」「好」这类等于没确认 |
| `echo` | **逐字等于**被武装对象的名字（账户号 / 策略名 / `"5000.00"`） | 手一点就点错账户 |

**方向性约束（比字段约束更重要）**：

- 授权默认 **12 小时到期**。过期不是"提醒"，是**直接当作未武装** ——
  否则忘了关，第二天开盘会带着前一天的授权上场。
- **撤销不需要确认**，且 `revoke(account)` 一次撤到底。
  打开要三道确认、关掉要一按就关，这个不对称是刻意的。
- `authorize(mode)` 的 `mode` **必须调用方显式传入**，Gate 不从标的/场所/配置推断。
  猜错模式就是真钱。

**决策结构**：

```json
{"allowed": false, "mode": "LIVE", "blocked_layer": "strategy:s1",
 "reason": "未武装或已失效（另有 2 项未通过：order_cap, reconciliation）",
 "checks": [{"level": "account", "ok": true,  "detail": "总敞口上限 60% NAV"},
            {"level": "strategy:s1", "ok": false, "detail": "未武装或已失效"},
            {"level": "order_cap", "ok": false, "detail": "未武装或已失效"},
            {"level": "reconciliation", "ok": false, "detail": "尚未对账"}]}
```

**`checks` 刻意不短路**：通过的也留痕，失败的并列全出。
事件要能回答「当时是哪几级开着的」，运维也要一次看到全部缺项。

`blocked_layer` 取第一个失败项（层级顺序：`nav` → `account` → `strategy:*` →
`order_cap` → 金额/额度 → `reconciliation`）。对账排在最后是因为它最容易修，
而「某级没武装」是更根本的问题。

**硬约束**：`NAV ≤ 0` 时一律拒。所有百分比上限都靠 NAV，
NAV 坏掉时 `0 × 任何比例都通过`，必须单独拦。

### D.2 日终四项对账（T-402）

**对账的输入是券商账单，本地账本只能向它靠。**

```
BrokerStatement{account_id, day, as_of, cash, positions,
                open_client_order_ids, trade_ids}
```

| # | 项目 | 本地取数 | 差异含义 |
|---|---|---|---|
| 1 | 现金 | `Ledger.cash_native()` | 手续费/成交价/漏记 |
| 2 | 持仓 | `Ledger.positions()` | 漏记成交 / 数量口径 |
| 3 | 挂单 | `OrderRegistry.active_orders()` | 本地在等券商已结束（回报丢失）；券商挂着本地不知道（可能有单被成交） |
| 4 | 成交 | 账本 `kind=TRADE` 分录的 `ref_id` | 券商有本地无 → **净值虚高**；本地有券商无 → synthetic 补录待确认 |

**判定语义（最重要的一条）**：

```
clean = statement_ok AND not diffs
```

`statement_ok=False`（网络/权限/券商维护）时**恒不干净**。
少了这一条，"取数失败"会被算成"零差异"—— 两者在净值上看起来一样，在风险上完全相反。

**其他约定**：

- 差异**只报不改**。`EodReconciler` 不得自动修账本、不得自动改订单状态。
  「自动抹平差异」是对账系统最危险的功能。
- 差异按危险度排序：`trade > open_order > position > cash`。
- 现金容忍默认 `0.01`（分），持仓默认 `0`。
- 报告原子落盘到 `state/eod/YYYY-MM-DD.json`。

**与实盘开关的耦合（硬性）**：日终跑完立刻 `LiveGate.set_reconciliation()`。
不干净 → 已武装账户立刻被拦；恢复干净 → 自动恢复（不必重新武装）。

### D.3 归因日报（T-403）

| 项 | 含义 | 口径 |
|---|---|---|
| `trading` | 策略收益 | 现价 vs 决策成本（含 slippage 效应） |
| `slippage` | 滑点 | 决策价与成交价之差 |
| `fee` | 手续费 | 恒 ≤ 0 |
| `funding` | 资金费 | B5 起非 0 |
| `fx` | 汇率 | **残差**，见下 |
| `net_return` | 当日净收益 | `nav_close - nav_open - 外部净流入` |

**关于"五项之和 = 净收益"**：因为 `fx` 是残差，这个等式**在构造上恒成立**，
它本身证明不了任何东西。真正当校验用的是两条**独立**规则：

1. 单一计价货币（所有汇率 = 1）时 `fx` **必须精确为 0**
2. `fee` **必须 ≤ 0**

任一条不成立 → 写进 `warnings`，不抹平。

**口径陷阱（会让人查一整天）**：策略分摊合计要与 `trading` 比，**不能与
`trading + slippage` 比**。`strategy_pnl` 用「归属市值 − 归属成本」，
其中成本已按决策价计，本身含 slippage 效应。

**首日无基线**：期初按「账户尚未开立」计（NAV 0、净流入 0），
`first_day=true` 并给出 warning —— 这一行是自开户以来的累计值，不是单日收益。

### D.4 净值时序

```
NavPoint{day, ts, nav, net_pnl, trading, slippage, fee, funding, fx,
         external_flow, gross_exposure, net_exposure, by_strategy{}}
```

- 存储：单个 JSON 数组文件，**按日 upsert**，整文件原子替换（`os.replace`）。
- 为什么整天重写而不是追加：**重跑日终是正常操作**，追加会写出两个同日的点，
  净值曲线就会莫名"抖"一下。幂等比性能重要。
- `previous(day)` 严格早于该日 —— 次日归因的基线。
- 没有点就是没有点：接口返回 `available=false` + `reason`，
  **不返回空数组**（空数组会让前端画出一条平线，看起来像"净值一直没变"）。

### D.5 新增只读端点

| 方法 | 路径 | 返回 |
|---|---|---|
| `GET` | `/api/ops/nav-history?limit=N` | `{available, count, points[], reason}` |
| `GET` | `/api/ops/live` | `LiveGate.status()`：`accounts` / `strategies` / `order_caps` / `reconciliation` / `live_ready` / `missing` |

两者都是只读。武装仍然只能通过 `LiveGate` 的 Python 接口 + 人工确认完成 ——
**没有一个 HTTP 端点能开实盘**，这是刻意的。

## 附录 E · 多场所契约（B5 / T-501~T-504）

> 归属：`gateway.py`（协议与错误）→ `venues.py`（能力与准入）→ `ccxt_gateway.py`（翻译）
> → `funding.py`（资金费）→ `scheduler.py`（多日历调度）。
> 分层是单向的：上层的模块 import 下层，反向没有路径。

### E.1 错误分类（网关层唯一的对外语义）

`GatewayError.ambiguous` 不是标签，是**允许上层做什么**的依据：

| 异常 | `ambiguous` | 允许的动作 |
|---|---|---|
| `TransportError`（网络/超时/连接重置/未分类异常） | **True** | 回查；**不得重发** |
| `RateLimited`（429/限流） | **True** | 回查；不得重发 |
| `VenueRejected`（余额不足/参数非法/标的不存在） | False | 当没发生过 |
| `AuthError`（凭证/权限） | False | fail-closed，不进重试循环 |
| `CapabilityError`（本系统不支持） | False | 一个请求都不发 |

两条硬规则：

1. **未分类异常一律翻译成 `TransportError`**（当不确定处理）。理由是不对称成本：
   多查一次几毫秒，重发一次双倍仓位。
2. **`CapabilityError` 发生时尚未接触网络**，因此它同时表达"订单确定不存在"。

### E.2 `submit_with_reconcile` 契约

```
输入  gateway + OrderIntent + max_queries
前置  capabilities.supports_client_order_id 且 supports_query_by_client_id，否则抛 CapabilityError
输出  SubmitOutcome{status ∈ {accepted, rejected, unknown}, reason, order, place_calls, queries}
保证  place_calls ∈ {0, 1}          ← 恒成立，永不为 2
      status=unknown ⇒ 不得重发，需人工或下一轮对账消解
```

`unknown` 是一个**合法终态**，不是待处理异常。它的语义是"系统已经尽力，
接下来属于人的工作"。

### E.3 能力矩阵与准入（T-502）

```python
Capabilities{
  venue, supports_client_order_id, client_order_id_param,
  supports_query_by_client_id,          # ← 与上一项缺一不可
  order_visibility_lag_ms,              # 下单后多久能被查到
  supports_reduce_only, supports_ws,
  funding_interval_hours,               # 0 = 现货，无资金费
  default_rules: SymbolRules{qty_step, price_tick, min_qty, min_notional},
  symbol_rules: {symbol: SymbolRules},  # 按标的覆盖，交易所本来就是分档的
  declared_from, verified_at,           # verified_at 为空 = 声明值未实测
}
```

**五条阻断线**（任一命中即 `admit().allowed = False`）：

| 条件 | 说明 |
|---|---|
| `not supports_client_order_id` | 超时后无法去重 |
| `not supports_query_by_client_id` | 超时后无法回查，状态永远不确定 |
| 任一标的 `qty_step <= 0` | 无法安全量化 |
| 任一标的 `min_notional > 单笔上限` | 假接通：准入通过但每单被拒 |
| `order_visibility_lag_ms > reconcile_budget_ms` | 订单永远卡在冻结态 |

告警类（不阻断）：无 WS、不支持 reduce-only、非标准资金费周期、`verified_at` 为空。

**取整方向是本契约的一部分**，不是实现细节：

```
数量       一律向下           向上 = 实际敞口大于风控算的敞口
买入限价   向下               限价是成本上限，向上就越过了它
卖出限价   向上               限价是收入下限，向下就越过了它
```

取整动作必须写进 `OrderCheck.notes` 并落审计，否则事后说不清"为什么实际下单
和意图不一样"。

### E.4 资金费口径（T-503）

```
金额 = signed_qty × mark_price × rate        正数 = 账户支出（与 post_funding 同向）
多头 × 正费率 = 支出      空头 × 正费率 = 收入      多头 × 负费率 = 收入
```

| 概念 | 是否进账本 | 用途 |
|---|---|---|
| `FundingAccrual`（盘中计提） | **否** | 让 NAV 曲线在两次结算之间连续 |
| `FundingPayment`（已结算） | 是 | 账本 `pnl:funding` |

幂等键 = `(场所, 标的, 结算边界)`。三种重放场景的行为：

```
同一笔再记一次        → duplicate=True,  不写账本
重跑 100 次日终       → 账本仍 1 条
交易所修正金额 6→6.5  → 只补差额 0.5，ref 加 #amend 后缀
```

对账口径与日终一致：`clean = statement_ok AND not diffs`。差异三类，
`missed`（交易所扣了、账本没记）最危险 —— 它让 NAV 偏高，风控会以为还有余量。

### E.5 调度契约（T-504）

```python
Lane(name, session, handler, interval_sec)
Scheduler(lanes).tick(now) -> {lane_name: LaneResult}
LaneResult.state ∈ {ran, failed, skipped_closed, skipped_not_due}
```

三条不可协商的行为：

1. **逐 lane 异常隔离**，捕获 `BaseException`（`SystemExit` 也不许带走兄弟 lane）。
2. **休市期间 `_next_due` 推后到 `now + interval`**，因此恢复交易时最多跑一次，
   不会补出整个休市期的节拍。
3. **`boundaries_crossed(prev, now)` 补账**：交易节拍不补，资金费账必须补。

日历契约：`EquitySession`（时区 + 开收盘 + 节假日 + 提前收盘 + 周末）、
`CryptoSession`（全天候 + 维护窗口）。`load_tz()` 取不到时区**报错而非退化成 UTC**
—— 静默退化的后果是在错误时间交易且日志全绿。

### E.6 分层与依赖

```
scheduler.py ──→ funding.py ──→ gateway.py ──→ venues.py ──→ contracts.py
     │                              │
     └──────────────────────────────┴──→ ccxt_gateway.py（只依赖上面两层，不反向）
```

`ccxt` **不在任何模块的顶层 import**，只在 `build_ccxt_transport()` 里延迟导入。
这样自测、回放、回环运维面在没装 ccxt 的机器上都能跑。

# 附录 F · 组合层契约（B6）

三个模块，三层职责，互不反向依赖：

```
ai_research.py  ← 只读，产出数据（不认识任何生产对象）

risk_budget.py  ← 风险 → 额度（消费 net_targets 的净额与 per_strategy）
```

## F.1 风险模型（`RiskModel`）

| 字段 | 类型 | 语义 |
|---|---|---|
| `vols` | `Mapping[symbol, Decimal]` | 年化波动率。**缺项抛错** |
| `corr` | `Mapping[(a,b), Decimal]` | 两两相关系数，`ρ(a,a)≡1` |
| `default_corr` | `Optional[Decimal]` | 默认相关。`None` = 必须显式声明 |
| `label` | `str` | 会出现在报告里，用于追溯"这是哪个假设" |

`default_corr is None` 且缺 `ρ(a,b)` 时抛 `RiskModelIncomplete`。
**不允许默认 0**：两个同向 Crypto 仓位被当成不相关，风险会被系统性低估一半，
而且这个低估不会以任何形式报错。

两种显式表态：`RiskModel.diagonal(vols)`（假设不相关，`default_corr=0`）、
`RiskModel.uniform(vols, rho)`（常数相关，label 固定写上 ρ 值）。

## F.2 风险分解（`PortfolioRisk`）

输入**必须是净额**（`net_targets` 的 `net_target_notional`），不是毛额。
函数参数名就叫 `net`，传毛额进来会得到一个偏大的数字，且同向重复计算从那里开始。

```
σ² = Σᵢ Σⱼ nᵢ nⱼ cov(i,j)
σ  = sqrt(σ²)
边际贡献ₖ = Σⱼ nⱼ cov(k,j) / σ
风险贡献ₖ = nₖ × 边际贡献ₖ
Σₖ 风险贡献ₖ ≡ σ            ← Euler 分解
策略i贡献 = Σₖ 风险贡献ₖ × (nᵢₖ / nₖ)
Σᵢ 策略贡献ᵢ ≡ σ            ← 按净额占比切分
```

| 属性 | 含义 | 断言 |
|---|---|---|
| `closes` | `Σ标的贡献 == σ` | ✅ 每份报告都断言 |
| `attribution_closes` | `Σ策略贡献 == σ` | ✅ |
| `standalone_sum` | 各策略独立波动之和 | 必须 `> sigma` |
| `diversification` | `1 - σ / standalone_sum` | 用于展示分散化收益 |
| `hedged` | 净额被对冲掉的标的 | 非空时必须告警 |
| `notes` | 对锁/无归属/自洽性异常的说明 | 不空则人看 |

**这两个恒等式证明不了输入是对的**（与 B4 归因日报同一个教训）。真正能抓错的：

1. `standalone_sum > sigma` 不成立 → 协方差矩阵不正定；
2. 单标的组合 `sigma ≠ |n| × σ` → 分解算错；
3. `sigma == 0` 但仍有净额 → 相关系数写成 -1 之类的自洽性错误；
4. `hedged` 非空 → 模型说无风险，真风险在基差与两腿时差（未建模）。

## F.3 等风险贡献（`equal_risk_weights`）

Spinu 坐标下降：目标 `wᵢ·(Σw)ᵢ = σ²/n`（对所有 i 相同），固定其它坐标时是关于
`wᵢ` 的一元二次方程，闭式求解。

**与倒数波动率的关系（容易搞错）**：

| 相关结构 | `1/σ` 是否等于等风险解 | 说明 |
|---|---|---|
| 对角线（ρ=0） | ✅ 相等 | 数学上就是答案 |
| 常数相关（ρ 全同） | ✅ **相等** | 易错点：很多人以为不相等 |
| 块相关（某簇内高相关） | ❌ 不等 | 这才是不用 `1/σ` 的理由 |

实测（A/B ρ=0.95，C 与两者 ρ=0.1，波动率全 0.5）：

```
1/σ 方案  权重 33.3/33.3/33.3  风险占比 38.7/38.7/22.6  σ=383,695
ERC 方案  权重 29.9/29.9/40.3  风险占比 33.3/33.3/33.3  σ=373,558
```

同一预算下 ERC 少承担 2.6% 的波动。结论对相关性假设极度敏感 —— 凡是用了
`default_corr` 的结果都会在 `notes` 里挂一条"这是假设不是估计"。

## F.4 风险预算 → 额度（`budget_to_quotas`）

```
quotaᵢ = budgetᵢ × risk_target_pct / σᵢ
Σquota > max_total 时整体等比压缩，压缩系数写进 notes
```

| 规则 | 行为 |
|---|---|
| `budgetᵢ = 0` | `quotaᵢ = 0`，并在 notes 写明"不给配额" |
| `budgetᵢ < 0` | 抛 `ContractViolation` |
| 缺 `σᵢ` | 抛 `RiskModelIncomplete` |
| `risk_target_pct ≤ 0` | 抛 `ContractViolation` |
| `max_total > 1` | 抛 `ContractViolation`（不允许预设杠杆） |
| 超上限 | 压缩 + notes，**绝不加杠杆把预算塞满** |

写回策略配置用 `apply_budget_plan()`：**只改 `quota_pct`，不改 `risk_budget_pct`**
（预算是输入、配额是结果，混在一起以后无法重算）。

`budgets_from_policies()` 在全为 0 时返回空字典 —— 调用方据此退回固定配额口径。
这是两套口径的切换开关，不要让它们同时生效。

## F.5 灰度队列（`Cohort` / `CanaryRouter`）

| 字段 | 语义 |
|---|---|
| `stable_version` | 稳定版版本号 |
| `canary_version` | 灰度版版本号（回滚/扶正后留档，不清空） |
| `weight` | 灰度版份额 ∈ [0,1] |
| `state` | `single` / `canary` / `rolled_back` / `promoted` |
| `retired` | 曾接流量、现已下线的版本集合 |
| `peak_weight` | 历史最高权重（复盘"曾经放到多大"） |

`shares()`：`single` 时 `{stable: 1}`；`canary` 时 `{stable: 1-w, canary: w}`。

`version_share(v)` 三分支：

| 版本状态 | 返回 | 理由 |
|---|---|---|
| 在 `shares()` 里 | 对应份额 | 正常 |
| 已知但已退役 | `0` → 意图**丢弃并记账** | 残留进程不能拖停整个基金 |

这条区分是 B6 里最实用的一处：把「忘了杀进程」和「放野版本进来」分开处理，

## F.6 路由规则（`route`）

| 情形 | 行为 |
|---|---|
| 策略不在路由表 | 原样通过（不做无依据的缩放） |
| 两个版本都发满权重 | 各 × 份额，合计 = 1.0 |
| 只有灰度版发 | 合计 = `w`，**不归一化** |
| 只有稳定版发 | 合计 = `1-w`，灰度份额不回流 |
| 份额为 0 | 丢弃 + `dropped` 计数 + notes |
| `reduce_only_hint=True` | **不缩放**，同策略同标的只留幅度最大的一份 |

两条最关键：

1. **不重新归一化**。把空出来的份额补给正在跑的版本，等于让灰度版承担全额风险，
   报表上却仍写着"只灰度了 10%"。
2. **reduce_only 不缩放**。把清仓按 0.1 缩放，结果是只清了 10% —— 方向恰好反了。

# 附录 G · 估计层与公司行动契约（B7）

> 这一层补的是附录 F 里那句「σ 和 ρ 由外部提供」。有了它，风险数字才有来源；
> 也有了新的失败模式 —— 估计本身可能是错的，而且错得很像对的。

## G.1 估计输入（`PriceSeries` / `EstimationConfig`）

```python
PriceSeries(symbol, points=[(date, close), ...])   # 日期升序、唯一、价格 > 0
EstimationConfig(annualization, halflife=None, shrinkage=0, min_obs=?, clip=?,
                 stale_after_days=?)
```

三条硬约束：

| 约束 | 违反时 | 为什么不能放松 |
|---|---|---|
| `annualization` **无默认值** | 抛 `EstimationError` | 股票 252 / Crypto 365，用错差约 20%；给默认值等于替用户押一个市场 |
| `points` 必须日期升序且唯一 | 抛错 | 乱序会让收益算反号，重号会让权重错位 |
| `close` 必须 > 0 | 抛错 | 0 或负值会产生无穷收益 |

**对齐用日期交集，绝不前值填充。** 填充出来的「价格没变」会被算成 0 收益，
于是 σ 被低估、同样的风险预算能买更多 —— 这是往危险方向偏的偏差。

**复权口径**：`close` 约定为**前复权**价。未复权价与复权价之间用
`adj_factor`（累计比值）换算：`未复权 = close / adj_factor`。
两种口径估出来的 σ 不一样：sh600000 的 400 天样本里，未复权口径高 **+2.0%**。

## G.2 估计输出（`CovarianceEstimate`）

```python
CovarianceEstimate(
    symbols, vols, corr, raw_corr, n_obs, n_assets, dof_ratio, corr_stderr,
    annualization, window, halflife, shrinkage, dropped, warnings, label,
    trustworthy, estimated_at,
)
```

| 字段 | 含义 | 页面怎么用 |
|---|---|---|
| `vols` | 年化 σ，按 `annualization` | 直接列出来 |
| `corr` | 收缩**后**的 ρ | 配对显示 |
| `raw_corr` | 收缩**前**的样本 ρ | 与 `corr` 并排，形成「样本 → 收缩后」 |
| `dof_ratio` | `n_obs / n_params`，`n_params = n + n(n-1)/2` | 并写出分母，`< 5` 判不可信 |
| `corr_stderr` | ρ 的标准误上界 | 收缩位移超过它 → 标「超分辨率」 |
| `shrinkage` | δ | 与 `raw_corr` 一起决定「这个数有多少是数据」 |
| `warnings` | 估计器自报的问题，原样透传 | 不裁剪、不合并、不改写 |
| `trustworthy` | 自检结论 | `False` 时整块判不可信 |

**`raw_corr` 必须存在。** 收缩能把 ρ 从 0.87 压到 0.62；只报收缩后的值，
看的人会以为 0.62 是估出来的。落盘（`to_dict`）同样带这份对比，
否则读回来的模型就只剩「结论」没有「结论是怎么来的」。

**`n = 2` 时收缩无效**：常数相关目标就是那唯一一对 ρ，收缩只是原地缩放。
这种情况必须显式告警，不能让人以为「已经做了稳健处理」。

## G.3 落盘（`RiskModelStore`）

```python
RiskModelStore(path).save(estimate)   # 原子替换
                  .load()             # -> CovarianceEstimate | None
                  .age_days(now)      # -> float | None
                  .stale(now)         # -> bool
```

- 原子替换：先写临时文件再 `os.replace`，半截文件不会被读到；
- `estimated_at` 缺失时 `age_days()` 返回 `None`，**不返回 0** ——
  0 意味着「刚刚估过」，那是编出来的新鲜度；
- 阈值：`> 7` 天 warn、`> 30` 天 critical。30 天是拍的，没有依据说 29 天一定安全。

## G.4 公司行动记账（`Ledger`）

```python
post_dividend(day, symbol, gross_amount, withheld_tax, currency, ...)
post_interest(day, amount, currency, ...)      # 融资利息，计入资金成本口径
apply_split(day, symbol, ratio, ...)           # 只改 qty 与 attr_qty
```

| 动作 | 改动 | **不许**改动 |
|---|---|---|
| 分红 | 现金 += 净额；`dividend` 项 += | 不动 `trading` |
| 融资利息 | 现金 -= 金额；`funding` 项 -= | 不给它单独开第七项（它是资金成本的一种） |
| 拆股 | `qty *= ratio`、`attr_qty *= ratio`、`avg_cost /= ratio` | **不改** `buy_at_decision` |

拆股改 `buy_at_decision` 会凭空造出收益：50 股 @180 拆成 100 股 @90，
`buy_at_decision` 仍是 9,000；改成 18,000 就等于承认赚了 9,000，而没有任何一笔成交能解释它。

**幂等门**：所有派生字段（`net_deposits_base` / `net_withdrawals_base` / 手续费累计 /
资金费累计）的累加都挂在 `Ledger.was_written(entry)` 之后。
重复回报让现金只加一次但派生字段加两次时，`net_pnl` 会凭空偏掉一大截，
而差额会被 fx 残差吞掉、恒等式照样闭合。

## G.5 对账第五项（`DiffKind.CORPORATE_ACTION`）

严重度排序（数值越小越靠前）：

```
TRADE 0  →  OPEN_ORDER 1  →  CORPORATE_ACTION 2  →  POSITION 3  →  CASH 4
```

公司行动排在持仓/现金**之前**，因为它是根因：一笔没入账的分红会同时造成
现金差异和持仓差异。先报现金差异，等于让运维去修症状。

| 情形 | 结论 |
|---|---|
| 券商声明了分红，账本有对应分录且金额一致 | 干净 |
| 声明了但账本没有 | 报 `CORPORATE_ACTION`：「未入账的分红」 |
| 拆股比例不一致（即使数量对上了） | 报 `CORPORATE_ACTION` |
| 预扣税不符（即使总额相同） | 报 `CORPORATE_ACTION` |
| 声明里出现未知类型 | 报「未知公司行动」，**不默认没问题** |
| 拿不到账单 | 判不干净（与 B4 同口径） |

对账**只读**：绝不自动补账。自动补账会把「记账错了」和「券商错了」变成同一件事。

## G.6 归因六项

```
trading + slippage + fee + dividend + funding + fx = net_pnl
```

`fx` 是**残差**：`fx = net - (trading + slippage + fee + dividend + funding)`。
所以这个等式在构造上恒成立，闭合本身证明不了没漏记 —— 分红被算进 `fx` 时它照样闭合。
真能抓错的是两条独立校验：

- 单一计价货币下 `fx` 必须**精确为 0**；
- 手续费必须 ≤ 0（`fee > 0` 说明记账方向反了）。

`NavPoint.dividend` 对老快照用 `d.get("dividend") or 0` 兼容 ——
B7 之前写的快照没有这个字段，读它不能炸，但也不能假装那天的分红是 0 以外的值。

契约要点：

1. **只读**。没有任何 HTTP 端点能改风险假设、灰度权重、研究条目。
2. 三块**各自**带 `available` / `reason`，而不是用空数组表示「没有」——
   空数组分不清「没有数据」和「功能没接上」。
3. 未接入时 `metrics` 里也会出现对应的 `not_configured` 指标，
   保证「页面上看不到」和「指标层看不到」是同一件事。
4. 页面把这块当**补充数据**：请求失败**不计入离线判定**，
   只让三块显示「看不到」，不影响其余五个请求的结论。

## G.8 只读端点 `GET /api/ops/schedule`

```
{
  as_of, available,
  calendar: { name, first_day, verified_until, source, holidays, warnings[] },
  signal_day,                  # 这一刻能拿到收盘价的最近一个交易日
  signal_day_covered,          # 该日期是否落在日历校准区间内
  calendar_gap,                # 空的表示已校准；否则是给人看的缺口说明
  close_at, timezone,          # 收盘口径（15:00 + 结算延迟）
  entry_count,
  entries: [ {
    strategy_id, version, kind, rebalance_days, anchor, key,
    offset,                    # 数据日相对锚点的交易日序号
    due_today, next_due, next_due_verified,
    last_run_day, last_run_at, last_decision, last_detail, last_outcome{},
    runs, failures, consecutive_failures, total_fills,
    claim_day, claim_at, in_doubt, healthy
  } ],
  needs_attention: [strategy_id, ...],
  healthy
} | { available: false, reason, entries: [], entry_count: 0,
    needs_attention: [], healthy: false }
```

契约要点：

1. **只读，而且结构上没有写能力。** 服务端拿到的是一个**返回快照的纯函数**
   （`schedule.status_snapshot`），不是一个 `RebalanceScheduler` ——
   看板不该握着 `tick()`，那等于给它一个下单按钮。
2. `available: false` 有四种来源，`reason` 必须区分：没接入 / 没日历 /
   没状态存储 / 快照读取失败。**「没有排期」和「看不到排期」不是一件事。**
3. `signal_day_covered: false` 时页面必须显示红，并且写明缺口。
   此时调度器拒绝运行（`REFUSED_NO_CALENDAR`），不是「按规则猜一天」。
4. `in_doubt: true` 表示**那一天可能已经下过单**。页面必须用当前状态覆盖
   `last_decision`（历史结论与当前状态同时显示会互相打架），并明说需要人工 resolve。
5. 与 G.7 同一条降级规矩：这块是补充数据，请求失败不计入整页离线判定。
