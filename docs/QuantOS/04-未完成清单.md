# QuantOS 2.0 · 未完成清单（B12 之后）

> 生成时间：2026-10-27
> 口径：**「设计要求里点了名，但代码里没有可运行路径」才算没做。**
> 只是「文档没写」「测试不够」不算 —— 那属于补齐，不属于缺失。
> 反过来，**代码写了但没人调它**也算没做（例如实现了灰度路由但没有策略运行时会去问它）。

当前规模：`quantos_core/` 40 个模块约 2.07 万行，控制台 `quantos/index.html` 4200 余行，
验收 15 套件 1788 条断言。**契约层、账本层、风控层、运维层、策略层、调度层、回测层
是完整的；网关层已有一条真实路径（Alpaca 纸面），部署层仍然空着。** 部署层恰恰是
「真钱」经过的地方。

## 1. P0 · 阻断真钱的三处结构性缺口

这三处不补，系统能算账、能风控、能看报表，但**一单也发不出去**；
或者更糟：能发出去，但发的是没经过准入的野单。

### 1.1 ✅ 已解除（B11，2026-10-27）：真实券商网关

原来这一节写的是「`fetch_order` 没有真实实现，超时先查交易所的逻辑只在假场所上验证过」——
**这是最容易自我欺骗的一处**，测试全绿只因为假场所永远按预期回应。

现在（`quantos_core/alpaca_gateway.py` + `scripts/quantos_alpaca.py`）：

| 项 | 现状 |
|---|---|
| 网关实现 | Alpaca 纸面账户，纯 stdlib REST，零第三方依赖 |
| 端点守卫 | 只认纸面；真钱要 `QUANTOS_ALPACA_LIVE=1` + `allow_live=True` 双开关 |
| 幂等 | `client_order_id` 冲突（422）→ 回查命中即成功；查不到判不确定，绝不重发 |
| 撤单 | 两步：先回查换 `order_id` 再 DELETE（实测该端点没有 `by_client_order_id`） |
| 真实往返 | `F` 1 股买 11.75 / 卖 11.74；场所现金 99999.99 = 账本现金 99999.99000000 |

**还剩什么没做**：

- **只到纸面**：真钱端点有开关但**没有任何真实资金联调证据**。
- **Crypto 仍是假 transport**：`CcxtGateway` 一行没改，`ccxt` 也没装。
- **A 股链路没接网关**：`tick` 的成交仍是 `PaperBroker`，Alpaca 是美股，
  两者只是共用同一套网关契约，标的不是同一批。
- **没接进风控/OMS 的实盘路径**：`place()` 是库，不是运行中的下单通道。
- **无 WebSocket**，全靠轮询；手续费按 0 记（SEC/TAF 未入账）。

### 1.2 ✅ 已解除（B8，2026-10-27）：策略运行时与导入契约

原来：`strategy_registry` 只存元数据、`strategy_adapter` 只做格式转换、`replay` 要外部喂 handler，
真正产生信号的策略躺在 `research/` 里，跟契约链没有关系。R-S05 说 5 个策略，接进生产平面的是 0 个。

现在（`strategy_api.py` + `strategy_pack.py` + `strategy_runtime.py`）：

- 策略有了明确形态：`MANIFEST` + `compute(frame, ctx)`，只产权重不产订单；
- 包导入有门槛：AST 体检 + 源码指纹 + 强制干跑 + 准入材料，导入只会进 RESEARCH；
- 整条链路第一次被同一次调用串起来：信号 → 意图 → 净额 → 风控 → 成交 → 账本 → 归因；
- `scripts/quantos_strategy_import.py` 一条命令给出"能不能导入"的判定。

**顺带修掉的两个真缺陷**：`policies()` 不看 stage（研究策略会被带进资金分配器）、
`REDUCE_REQUIRED` 无人接（超单笔上限的仓位永远建不起来）。

仍未做的：`rebalance_days` 还没有调度器读它（B9 已补）；~~没有回测引擎~~（B12 已补）。

### 1.3 ✅ 已解除（B9，2026-10-27）：策略不会自己跑

原来：`strategy_runtime.run_once()` 要人手敲，`rebalance_days` 只被记录、没人读。
现在（`calendar.py` + `schedule.py` + `scripts/quantos_schedule.py`）：

- 交易日历从真实行情反推，155 个休市日与 2026 年实际放假安排逐条吻合；
- 到期判定按**交易日**、从**固定锚点**算，漏跑不漂移；
- claim → run → complete 三段落盘，重启不重跑，跑没跑成有三种状态；
- 「收盘 + 结算延迟之前不算当日」写进 `signal_day()`，防前视偏差；
- 排期上屏，缺日历 / in_doubt 都显示红。

仍未做的：Crypto 24/7 的排期还没接。

### 1.3b ✅ 已解除（B10，2026-10-27）：每拍都是一份新账本

原来：`Ledger` 只有内存态，`AshareRunner` 每次启动都 `deposit()` 重建，
独立进程跑第二拍会把已有持仓当成 0 重新买一遍；更隐蔽的是幂等索引
`_refs`/`_by_key` 也跟着消失，重复成交回报会被再记一次。

现在（`state_store.py` + `ledger_store.py` + `quantos_tick.py` + `quantos_up.py`）：

- 整份快照原子落盘（含持仓成本、滑点、策略归属、派生字段），首次启动才建仓；
- 恢复时**从分录重建幂等索引**，重复成交/分红/拆股都只算一次；
- 坏档、版本不符、写一半，三种都拒绝运行（`must_load` 直接抛，不顶空账本）；
- cron 一拍一进程 + 单实例锁，退出码 0/1/2/3 分级（拒绝运行 = 2，不再伪装成"今天没事"）；
- 顺带修掉 `apply_split` 不幂等的真 bug（重放会把持仓乘第二次）。

仍未做的：**没有真实网关**（成交走 `PaperBroker`）、tick 仍用进程内风控引擎、
账本无 compaction、`quantos_up.py` 只做状态与启停不做守护重启。

## 3. P2 · 已上线但带病运行的

| # | 现象 | 为什么算病 |
|---|---|---|
| 3.1 | 页面探针是 **DOM 桩，不是浏览器** | 能抓数字漂移/漏字段/编绿灯，**抓不到 CSS 布局**。布局靠 headless Chrome 截图人工看，而 Chrome 下限 500px，390px 真机宽度**命令行验不了** |
| 3.2 | 能力矩阵五家交易所的步长/精度/最小额**都是抄文档的** | `verified_at` 为空即证据。上真钱前必须 `probe()` 实测 —— 这条写在「三条不要做的事」第 1 条 |
| 3.3 | 资金费符号 | 本地口径已固定并断言，但 CCXT 各场所 `info` 层的符号差异**要第一笔真实结算才能确认** |
| 3.4 | 复权口径实证只做了 **1 只**（sh600000，+2.0%） | 结论方向可信，样本量不够下一般性结论 |
| 3.5 | A 股场所 `xshg` **声明了「无法按客户端订单号回查」** | 结构准入会拒它，所以 A 股**不能上实盘**。回测只借它的规则矩阵（整手/涨跌停/最小金额）。真要让 A 股上线，得先有能按 client_order_id 回查的券商接口，把这条声明改成 `True` 并跑过 `probe()` |
| 3.6 | 回测**不模拟限价排队、不模拟盘中路径** | 日线只有 OHLC，「信号日收盘出单 → 次日开盘成交」是最理想的假设；真实排队可能整天不成交。这条无法靠日线消除，只能在报告里如实写 |

## 5. 刻意偏离项（不是遗漏，是选择）

R-M 技术选型表里的东西**一个都没上**：Next.js + FastAPI + Redis Streams +
PostgreSQL/TimescaleDB + Parquet/DuckDB + LEAN + Prometheus/Grafana。

现状是 **纯 stdlib Python（系统 python3 3.9 就能 import）+ 单文件 HTML**。

这是有意的：零依赖带来的可移植性，在这个阶段比水平扩展能力值钱。
但要清楚代价 —— **一旦标的数、策略数、事件量上去，会同时撞三堵墙**：
进程内状态（无 Redis）、单机文件（无 PG）、手写图表（无 Grafana 告警）。
迁移不需要推翻契约层，但需要重做所有 `Store` 的后端实现。

**用户已提过的下一步**：策略研究与回测也要在平台上跑。两件地基（账本持久化 B10、
回测引擎 B12）都已完成 —— 「换个地方手工敲脚本」这件事现在不会再发生了。

**B12 之后剩下的确定性**：网关层有一条真实路径，但**真钱联调仍然没做过**。
那一步需要两件事同时就绪：T-404 的两周小额观察期，以及把 `AlpacaGateway`
接进 `tick` 的下单链路（现在 `place()` 还只是一条库函数）。这两件事都不是
「再写一批代码」能解决的 —— 前者要时间，后者要真钱。

**B12 顺带证明了另一件事**：回测不只是"算收益"，它还是一条**把实盘路径压出来**的
压力装置。这一批修掉的两个 bug（部分成交时归属按下单量记、风控用昨天的 NAV）
都不在回测代码里，而在 `replay.py` / 决策时序上 —— 它们只在"几千笔真实撮合、
天天调仓"的量级下才显形。所以 B13 因子模型值得排在前面：风险层是现在唯一
还没被同样压力检验过的环节（30 只以上自由度就告警，而回测已经能跑 794 只）。

**不建议现在做的**：参数级灰度、`CanaryRouter` 持久化重建、分红税规则建模。
这三个都是「有真钱在跑之后才会疼」的问题，现在做等于给没人走的路修路灯。
