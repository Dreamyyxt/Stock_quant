# QuantOS 2.0 · 现状差距分析

> 生成时间：2026-10-26。对照 `00-系统要求.md` 逐域核对真实代码，不臆测。
> 结论口径：**已有**＝可直接复用；**部分**＝有基础但契约不匹配需改造；**缺失**＝需新建。

## 2. 逐域差距

### 架构 R-A

| 编号 | 要求 | 现状 | 结论 |
|---|---|---|---|
| R-A01 | 研究/生产双平面 | 单机单体，研究脚本与实盘共用同一目录 | **部分**：算力分离靠部署，代码未分层 |

| R-A08 | 订单故障恢复 | 有超时撤单 + 状态轮询 + 重试；状态归一含 `unknown`；**无稳定 client_order_id** | **部分（高危）**：超时重试缺幂等键，存在重复下单风险 |

## 3. 四条关键结论

**结论 1：最危险的不是缺功能，是 R-A02 + R-A08。**
风控是库不是服务，进程崩了风控一起消失；订单超时重试没有幂等键。这两条直接决定「真钱会不会被重复下两次单」。**必须最先解决，优先于任何新策略。**

**结论 2：R-A07 + R-C01 + R-D01 是同一个问题的三个面。**
没有跨策略净额、没有资金分配、没有策略归属台账 → 两个策略同时做多 BTC 时，系统会当成两笔独立交易，风险被重复计算而资金被重复占用。这三条必须一起设计、一起落地。

**结论 3：Crypto 是纯新建，但不要先做 Crypto。**
正确顺序是把「契约层 + 资金 + 风控 + 台账」在**股票单市场**上先跑通，再接 Crypto。否则会在两套网关的差异里同时调试业务逻辑，故障无法定位。

> **B5 之后的状态**：顺序被遵守了 —— B0~B4 把契约/风控/账本/实盘开关在单市场跑通，
> B5 才接多场所。而且 B5 没有直接接 CCXT，先建了场所无关的网关抽象与能力矩阵，
> 让"换一家交易所"只影响翻译层。**结论本身依然成立，只是前提已经满足。**

**结论 4：原型控制台不能当后端验收依据。**
`quantos/index.html` 早期所有数字都是 `defaultState()` 里的常量，它证明的是「界面能不能表达你的管理意图」，不是「系统能不能交易」。

> **B3 之后的状态**：页面已改为默认读 `/api/ops/*`，取不到才回退演示数据并**显式标注**（不再静默混用）。
> 但结论本身依然成立：**验收看 `scripts/quantos_ops_check.py` 的「接口 vs 进程内对象」比对，不看页面。**
> 页面只是渲染层，换掉前端不应该改变任何结论。
>
> **B7 之后补的一条**：页面渲染层现在也有自己的验收 —— `scripts/page_probe.js` 用零依赖 DOM 桩
> 跑真实脚本，逐项比对「页面上的数字 == 后端 JSON」。它抓得到数字漂移、漏字段、
> 拿不到数据时编绿灯，但**抓不到 CSS 布局**。布局靠 headless Chrome 截图人工核对。
> 这条不与结论 4 冲突：探针验的是「渲染是否忠实」，不是「系统能不能交易」。
