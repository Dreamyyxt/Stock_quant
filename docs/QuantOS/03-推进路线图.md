> 排序原则：**按「真钱会不会被搞没」排序，不按「功能看起来爽」排序。**

### B3 期间修复的两个真实语义缺陷

1. **「没发意图 ≠ 要清仓」（解掉 B0/B1 遗留的整标的阻断）**
   原 `net_targets` 对每个标的算总差额，任何策略 `PAUSED` 就会把整个标的的调仓停掉。
   改为按策略算差额（`NettingInput.current_by_strategy`）：
   - `PAUSED` → 冻结该策略存量，不参与新增净额
   - `REDUCE_ONLY` → 只允许减少自身敞口，不许反向、不许加仓
   - **该策略本轮没发意图 → 冻结存量，不当作目标 0 去清仓**
   - 无归属残差（净额与各策略之和不一致的部分）→ 冻结并记 `notes`

2. **`by_strategy={}` 曾被当成「已提供」**
   空字典 `bool()` 为 False 也是这次才用对：`use_strategy_level = bool(by_strategy)`。
   直接把空 dict 走策略级算法会算出与整标的算法不同的净额（-6000 vs -8000）。
   现在明确：**空字典等价于未提供，退化为整标的算法。**

顺带补的两条：`CapitalAllocator` 不再过滤 0 值权重（`target_weight=0` 是清仓的**显式表达**，
过滤掉就等于不执行清仓）；`OrderRegistry.orders()` 提供只读快照给运维层，避免运维拿可变引用改状态。

### 验证时才发现的一个可用性问题：基线一直是红的

`build_runtime()` 原来在默认场景里就挂着一笔待对账订单，于是**任何一次** `--once`
都是 `overall=critical`、headline 永远是 `orders · …`。四个故障注入看起来完全一样，
"能定位到具体环节"这件事等于**根本没被验证过**。

改法：基线最差只到 `warn`（OKX 通道降级 + 一个仅减仓策略），待对账订单只在
`--fault unknown-order` 时造出来。现在每个故障的 headline 都指向自己的组件。

这条的普适教训：**长期挂着未处理告警的系统等于没有告警。**
验收脚本本身也是一个系统，它的基线状态必须是"健康"，否则断言全绿但什么都没证明。

### B4 DoD 达成证据

**一、「少一级确认就无法下单」是可执行的事实，不是约定**

三级各自独立武装，每次武装要过三道确认（人工 actor / 至少 6 字理由 / 逐字回显对象名）。
少任何一级都拒单，并且**一次列出全部缺项**，不用「改一个刷新一次才发现还缺一个」：

```
allowed=False layer=account  未武装（另有 3 项未通过：strategy:s1, order_cap, reconciliation）
allowed=False layer=strategy:s1  未武装或已失效（另有 2 项未通过：order_cap, reconciliation）
allowed=False layer=order_cap    未武装或已失效（另有 1 项未通过：reconciliation）
allowed=False layer=reconciliation  尚未对账
allowed=True  layer=-            三级授权齐全
```

另外几条硬约束（都有断言）：

- **AI 不能武装实盘**：actor 必须以 `human:` 开头。
- **回显必须逐字等于账户号 / 策略名 / 金额**，填错一次就打不开（防点错账户）。
- **授权默认 12 小时到期**，过期不是"提醒"而是**直接当未武装**。
- **撤销不需要确认**，且一次能撤到底 —— 关闭必须比打开容易。
- **NAV 不可用时一律拒**（0 × 任何比例都通过，必须单独拦）。
- **单笔上限没有默认值**，不显式设就是未武装；设了也会被 `10% × NAV` 再压一次。

**二、日终四项对账：拿不到账单 ≠ 对上了**

B0 的 `Ledger.reconcile` 只对现金与持仓。真钱最容易出事的是另外两项：

| 差异 | 本地 | 券商 | 后果 |
|---|---|---|---|
| 成交 | 未入账 | 有成交 | **账本漏记 → 净值虚高** |
| 成交 | 已入账 | 无此成交 | 本地记了券商不认的（多为 B2 的 synthetic 补录） |
| 挂单 | 仍在等 | 已结束 | 成交/撤单回报丢失，持仓未知 |
| 挂单 | 无记录 | 挂着 | 券商有单本地不知道，随时可能成交 |

`EodReconciler.run()` 拿不到账单时返回 `statement_ok=False` 且 `clean=False` ——
**"没对成"和"对平了"在净值上看起来一样，但在风险上完全相反**。

差异按危险度排序（成交 > 挂单 > 持仓 > 现金），运维先看最要命的那条。

**三、对账与实盘开关的耦合点**

`EodService.run()` 跑完立刻把结果写回 `LiveGate.set_reconciliation()`：

- 对账干净 → 三级授权仍有效的账户**自动恢复**可实盘（不需要重新武装）
- 对账不干净 → 已武装的账户**立刻被拦**，`blocked_layer=reconciliation`
- 两者都有断言（B11/B12/B13）

这条耦合是 B4 的核心：**对不上账还允许下真钱单，等于所有记账逻辑都白做。**

**四、归因日报：五项之和等于当日净收益，但这不是证明**

五项（策略收益 / 汇率 / 手续费 / 滑点 / 资金费）之和恒等于当日净收益，
因为**汇率项是按残差算的** —— 这个等式在构造上成立，它证明不了什么。

真正能抓错的是另外两条**独立**校验：

1. 单一计价货币（所有汇率 = 1）时，汇率项必须**精确为 0**
2. 手续费项必须 **≤ 0**（费用不可能带来收益）

这两条破了说明有一笔钱记到了不该记的地方。报表里 `warnings` 会把它们列出来，
**不假装闭合就完事**。另外策略级分摊与 `trading` 同口径比对（口径错了就永远对不上，
所以必须与 `trading` 比而不是与 `trading + slippage` 比）。

**五、净值时序（顺带解掉 B3 遗留）**

`NavSeries` 按日 upsert（同一天重跑日终不会写出两个点），原子替换落盘。
页面改成：有 ≥ 2 个真点就画真曲线并标注「净值来自 N 个日终快照（真实）」；
点不够就显示占位并说明缺什么 —— **不拿演示曲线顶上**。

### B4 期间发现并修掉的一个问题

**演示运行时的"对账永远对得上"是假的对账。**
最初 `_DemoBroker` 用一个写死的正确账单，结果 `eod-mismatch` 故障注入无处可注入、
T-402 的四项差异一条都演示不出来。改为「账单由当前账面状态生成 + `cash_bias` 参数制造差异」后，
`--fault eod-mismatch` 才能真的把 `live.ready` 打到 0。

教训同 B3 的基线问题：**能演示"对得上"但演示不了"对不上"的验收，等于没验收。**

### B5 DoD 达成证据

**一、「超时不重发」是可执行的事实，不是纪律要求**

这条是整批的核心。绝大多数重复下单事故不是因为忘了幂等键，而是某处代码
把 `TimeoutError` 当成"失败了"，然后重试。所以错误分类里 `ambiguous` 是**语义**，
不是标签：

| 异常 | 归类 | ambiguous | 上层该做什么 |
|---|---|---|---|
| `NetworkError` / `RequestTimeout` | `TransportError` | **True** | 只能去查，不许重发 |
| `RateLimitExceeded` | `RateLimited` | **True** | 同上（429 未必所有场所都守约） |
| `InsufficientFunds` / `InvalidOrder` | `VenueRejected` | False | 确定没下出去，可当没发生 |
| `AuthenticationError` | `AuthError` | False | fail-closed，不当偶发重试 |
| `NotSupported` | `CapabilityError` | False | 本地就该知道，一个请求都不发 |
| **任何没见过的异常** | `TransportError` | **True** | 保守兜底：宁可多查一次 |

最后一行最容易被嫌"太保守"，但反过来想：未知异常当"确定失败"，上层就会重发，
而重发在交易所看来是一笔全新的订单。**成本不对称**——多查一次的代价是几毫秒，
重发的代价是双倍仓位。

`submit_with_reconcile()` 的实测行为：

```
正常提交                          → accepted  place_calls=1  queries=0
场所拒绝（余额不足）              → rejected  place_calls=1  queries=0
超时 + 订单其实落地 + 回查命中    → accepted  place_calls=1  queries=1
超时 + 真的没落地 + 回查 3 次未中 → UNKNOWN   place_calls=1  queries=3
连抛 3 个超时异常                 → UNKNOWN   place_calls=1
回查第一次也超时、第二次命中      → accepted  place_calls=1  queries=2
回查鉴权失败                      → UNKNOWN   place_calls=1  ← 不能因为查不了就当成交
无客户端单号 / 无法按单号回查     → 抛错      place_calls=0  ← 一个字节都没发
```

`place_calls` 恒为 1 或 0，**永远不会是 2**。

**二、能挂单 ≠ 能自动交易：准入的五条阻断线**

币圈的差异不在"有没有 API"，而在几个要命的细节。五条阻断线，每条对应一个具体事故：

| 阻断条件 | 事故形态 |
|---|---|
| 不支持客户端单号 | 超时重发即重复下单 |
| **支持发单号但无法按单号回查** | 超时那一刻既没 orderId 也查不回，**这笔单永远查不清** |
| 缺数量步长 | 只能瞎猜小数位，猜多那一次就是超敞口 |
| 最小名义 > 单笔上限 | 任何订单都被最小额拒绝 —— **假接通，监控还是绿的** |
| 下单可见延迟 > 对账预算 | 查不到就判 UNKNOWN，订单永远卡在冻结态 |

第二条最隐蔽：很多场所支持传 `clientOrderId`，但查询接口只认自己的 `orderId`。
**只有前者等于给自己造了"看起来有幂等键、实际上救不回来"的错觉**，所以
`supports_client_order_id` 和 `supports_query_by_client_id` 缺一不可。

第四条是这次写测试时**顺手修掉的真漏洞**：`admit()` 原本只看 `default_rules`，
而交易所的最小名义是按标的定的。默认 5 USDT、但你要交易的 BTC 是 100 USDT
的情况很常见 —— 准入通过、然后每一单都被拒。现在逐标的检查并指认最差的那个。

**三、取整方向：只能往"更小、更不容易成交"的方向**

```
数量   一律向下取整   向上取整 = 实际敞口大于风控算的敞口，风控数字全废
买入限价 向下取整     限价是你能接受的**上限**，向上就越过了它
卖出限价 向上取整     限价是你能接受的**下限**，向下就越过了它
```

三种取整都会降低成交概率，但都不会让账户承担超出意图的风险。
**宁可这一单不成交，也不能成交了才发现成交在预算之外。**

**四、资金费：三个口径陷阱**

```
多头(+2) × 30000 × 0.0001 = +6   → 支出 6（多头付钱，正常）
空头(-2) × 30000 × 0.0001 = -6   → 收入 6（空头收钱，正常）
多头(+2) × 30000 × -0.0001 = -6  → 收入 6（负费率反收）
```

1. **CCXT 的 `amount` 是现金流方向（付出为负），账本 `post_funding` 是费用方向
   （支出为正），必须取反。** 这个符号搞反的后果极隐蔽：账本总额还能对上账单
   （两处同时反了），但归因里 funding 项方向相反，等于把稳定成本记成稳定收益。
2. **应计 ≠ 已结算。** 盘中计提只进展示（`FundingAccrual`），账本只记
   `FundingPayment`。计提入账会在真结算时双记，而三个月后没人分得清哪笔是估算。
3. **按结算边界幂等，不是按执行次数。** 键是 `(场所, 标的, 结算边界)`。
   重跑 100 次日终，账本仍然只有 1 条；交易所事后修正金额时**只补差额**
   （记 6 → 改 6.5 时补 0.5，而不是重记 6.5 让人去猜哪笔作废）。

**五、24/7 与股票时段：三条规矩**

```
09:00 ET  开盘前    equity=skipped_closed   crypto=ran
09:35 ET  开盘中    equity=ran              crypto=ran
17:00 ET  收盘后    equity=skipped_closed   crypto=ran
```

1. **异常隔离**：一条 lane 抛异常（连 `SystemExit` 也算），另一条照常运行。
   捕获的是 `BaseException` 而非 `Exception` —— 这是刻意的：实盘里
   "因为 A 策略报错导致 B 策略不再运行"是真实发生过的连环事故。
2. **收盘不补跑**：休市期间每次 tick 都把下次到期推到"现在 + 间隔"，
   周一开盘只跑一次，不会把周末的节拍一次性倒出三千次信号。
3. **结算不遗漏**：`boundaries_crossed(prev, now)` 告诉你睡过了哪几个结算点。
   交易节拍不补，**账必须补** —— 漏掉的资金费是已经发生的现金流，
   不补的话 NAV 一直偏高，风控会以为还有余量继续下单。

时区处理有一条硬规则：**取不到时区就报错，绝不静默退化成 UTC**。
退化后美股会在 UTC 09:30 开盘，那是纽约凌晨 4:30 —— 系统不崩、日志全绿，
只是在错误的时间交易。

### 本次修掉的问题

- `admit()` 只看默认规则、漏掉按标的的覆盖 → 假接通（见上文第二条证据）。
- `ccxt_gateway` 首版在 f-string 里用了未转义的双引号 → 语法错误，编译时暴露。

### 已知限制（写进 README，不藏）

1. **真实交易所一次都没联调过。** 五家能力矩阵全是声明值（`verified_at` 为空），
   体检脚本里刻意标 ⚠️ 而不是 ✅。要真下单得装 ccxt、配凭据、跑 `probe()`

### B6 DoD 达成证据

**证据一：风险分解是恒等式，不是估算**

```
σ = 739,851.88（占 NAV 7.40%）
Σ标的贡献 = 739,851.88     Σ策略贡献 = 739,851.88
恒等式闭合：标的 ✅  策略 ✅
```

Euler 分解 `Σ nᵢ·(Σⱼ nⱼcovᵢⱼ)/σ ≡ σ` 在 `PortfolioRisk.closes` 与
`attribution_closes` 两个属性上各断言一次。**但这两个恒等式本身证明不了输入是对的**
（和 B4 归因日报同一个教训），所以另设三条真能抓错的检查：

- `standalone_sum > sigma` 必须成立 —— 有分散化就必然如此，反了说明协方差矩阵不正定；
- 单标的组合下 `sigma` 必须精确等于 `|n| × σ`；
- 完全对锁时 `sigma = 0` 必须同时产出 `hedged` 标记与告警。

**证据二：同向不重复计算（DoD 原文）**

```
两策略同向各买 10 万 BTC → 组合 σ = 120,000（= 20 万 × 0.6，只算一次）
  s1 承担 60,000 / s2 承担 60,000，Σ = 120,000 = σ
```

而踩坑的地方在**不同标的但相关**：

```
朴素相加（不扣相关）  130,000
真实 σ（ρ=0.5）        112,694   ← 差 17,306 全是重复计的共同因子
```

这里有个值得记下来的发现：**同一标的下「各自算再相加」与净额算法数值完全相同**
（风险对同一标的是线性的）。也就是说，只用单标的场景测这个 bug 永远测不出来 ——
它只在跨标的、相关时才暴露。验收脚本把这件事本身写成了一条断言。

**证据三：灰度 10% 不会变成 100%**

```
v3=0.900, v4=0.100
两版各发满权重 → 路由后合计 1.000（不是 2.0）
只有灰度版发信号 → 合计 0.100（不把稳定版的 0.9 补给它是关键）
只有稳定版发信号 → 合计 0.900（灰度份额不回流）
未知版本 v9 → 抛 UnknownVersion
```

「不重新归一化」是这组里最反直觉、也最重要的一条：把空出来的份额补给正在跑的版本，
等于让灰度版承担全额风险，但报表上仍然写着"只灰度了 10%"。

**证据四：自动化只能降不能升**

```
auto(ok)      0.4 → 0.4
auto(degrade) 0.4 → 0.2 → 0.1
auto(abort)   0.1 → 0
权重序列单调不增 [0.8, 0.8, 0.4, 0.4, 0.2, 0.1]
```

提权重、开灰度、扶正三条路径全部要求 `human:` 前缀；降权重、回滚对任何 actor 开放。
`auto_adjust()` 里**没有**提高权重的分支，而且留了一行防御性断言 ——
真触发了就是代码错。

**证据五：AI 通道没有写生产的路径（结构约束，不是纪律要求）**

```
assert_isolated() → {'bad_imports': [], 'forbidden_methods': [], 'ok': True}
```

做法不是加权限判断，而是让这个模块**根本不 import** `strategy_registry` /
`live_gate` / `oms`：没有 registry 引用，就没有 `registry.promote()` 可调。
用 AST 扫描代替字符串匹配（注释里提这些名字是正常的，字符串匹配会把说明文字判违规）。

```
payload.quota_pct                        → 拒绝（顶层禁用键）
payload.suggest[0].changes.armed         → 拒绝（递归到嵌套，理由带完整路径）
候选参数无 bt:/replay: 证据               → 拒绝
top_n: 1 → 5（+400%）                    → 拒绝（量级跳变）
reviewer="ai:reviewer"                   → 拒绝（AI 复核 AI 等于没复核）
prepared_by="ai:agent"                   → 拒绝（草案必须人签名）
```

出口只有一个 `ResearchDraft`：一份**数据**，必须 `human:` 签名产出，交给生产侧是
人的动作。

### 本次修掉的问题

- **对锁组合不告警**。`portfolio_risk` 早先写成 `if sigma > 0` 才建 `by_symbol` 条目，
  结果完全对冲的组合既没有 `hedged` 标记也没有告警 —— 一个看起来"零风险、很干净"的
  空列表。而这恰恰是最该有人看一眼的情形。
- **标的集合只从净额取**。净额被对冲成 0 的标的在 `net` 里只剩一个 0，只按 `net` 筛
  会在第一步就把最需要告警的情形筛掉。改成「净额有值 **或** 策略持仓有值」。
- **回滚后残留进程会拖停整个基金**。灰度版回滚后进程可能还活着、还在发意图；
  首版对"退役版本"也抛 `UnknownVersion`，一次回滚失败会让整轮路由中断 ——
  所有策略一起停摆。改成区分「已知但已退役（丢弃并记账）」与「从没见过（抛错）」。
- **`auto_adjust` 先判状态再校验判定值** → 「已回滚 + 判定值拼错」被静默放过。
  一个错字就让自动化悄悄失效。调换顺序，校验在前。
- **reduce_only 去重键含版本** → 两个版本都喊清仓时各留一份，变成两倍减仓。
  键里去掉了版本：同一策略同一标的的清仓是同一件事。
- **`assert_isolated` 白名单用裸 `startswith`** → `astropy` 会被当成 `ast` 放行，
  白名单形同虚设。改成只认精确匹配或带点的子模块。
- **ERC 的注释说法错了**。原文写"加进正相关后 1/σ 就会失效"，但**常数相关**矩阵下
  倒数波动率恰好就是等风险解（可证）。真正失效的是**块相关**：A/B 相关 0.95、C 只有 0.1
  时，1/σ 给出 38.7%/38.7%/22.6% 的风险分布，ERC 给出 33.3% 三等分，
  组合波动从 383,695 降到 373,558。注释和验收场景都改成了块相关。

### 已知限制

1. **波动率与相关性全靠外部输入。** 本模块不做估计，缺 σ 缺 ρ 一律抛错。
   这是刻意的（编一个 15% 会让报告看起来精确），但也意味着 B6 只解决了"给定假设怎么摊"，
   没解决"假设从哪来"。协方差估计属于研究层，目前没有实现。
2. **风险预算与固定配额是两套口径，不能同时生效。** 两者都产出 `quota_pct`，
   谁生效由配置决定。同时用两套算同一个策略，两边都会说自己对。
3. **策略级风险归因在净额为 0 时无意义。** 对锁组合的占比无法按净额切，
   本模块给 0 并告警。真实风险（基差、两腿时差）没有建模。
4. **灰度只到版本级，不到参数级。** 同一版本内改参数（比如 lookback 20→18）
   没法灰度，只能整版灰度或整版回滚。
5. **`CanaryRouter` 是纯内存的。** 进程重启后路由表丢失，靠审计日志重建；
   重建函数本次**没有**实现（`replay_from_audit` 是 B3 给 `StrategyRegistry` 的，
   没搬过来）。重启后必须先 `register_stable` 再 `open_canary`。
6. **AI 通道的隔离靠 import 图，不靠运行时权限。** 有人在别的模块里
   `from quantos_core import strategy_registry` 然后把 registry 传进研究流程，
   AST 扫描管不到 —— 它保证的是"本模块不自带写生产的能力"，不是"AI 永远无法影响生产"。
7. **`ResearchDraft` 只是数据，没有任何签名校验。** `prepared_by="human:owner"`
   是一个字符串前缀，不是密码学签名。防误触，不防伪造。

### B7 DoD 达成证据

**证据一：收缩前后一起给，因为收缩能把结论改掉**

```
            样本值     收缩后     Δ
QQQ / SPY   0.866  →  0.622   -0.244   ← 超分辨率
QQQ / TLT  -0.376  → -0.247   +0.129   ← 超分辨率
SPY / TLT  -0.332  → -0.217   +0.115   ← 超分辨率
```

ρ 的标准误上界 0.0791。三对的相关性被移动的幅度**全部超过统计噪声**，
也就是说：页面上那个 0.622，主要成分不是「市场相关性」，而是「我们选择了 δ=0.3 往均值拉」。
只显示收缩后的值，等于把这个人为选择说成观测事实。所以：

- `CovarianceEstimate` 额外保留 `raw_corr`，页面永远两个数一起显示；
- Δ 超过 `corr_stderr` 的对标「超分辨率」，不让人把它当真；
- 断言层面卡死：`raw_corr` 缺失就不许落盘（`to_dict` 带对比字段）。

**证据二：自由度比的分母是参数个数，不是标的个数**

```
3 标的 / 160 观测
  按标的算：160 / 3   = 53.3   ← 看起来极其充裕
  按参数算：160 / 6   = 26.67  ← 真实自由度（3 个 σ + 3 个 ρ）
5 标的 / 40 观测
  按标的算：40 / 5    = 8.0    ← 看起来还行
  按参数算：40 / 15   = 2.67   ← 实际已经不可信，触发告警
```

这是本批最容易自我欺骗的一处：用标的数当分母，任何面板都显得样本充足。
页面和指标层都直接写明「160 观测 ÷ 6 个待估参数」，让看的人自己复核分母。

**证据三：真实 A 股数据体检（794 只里的 3 只，400 个交易日）**

```
sh600000   σ = 24.0%    sh600004   σ = 16.8%    sh600009   σ = 18.1%
自由度比 66.50 · ρ 分辨率 ±0.0501 · 收缩 δ=0.3
```

**复权口径实证**：同一份数据两种口径各估一次。`sh600000` 在样本期内有 340 次除权
（只有分红除权，没有拆股），未复权口径的 σ 比前复权高 **+2.0%**。
这个方向的偏差是危险的：σ 被低估 → 同样的风险预算能买更多 → 实际敞口超标。

**证据四：分红不单独占项，就会被 fx 残差吃掉（真实修掉的 bug）**

```
除权日：现金 +1,000，市值 -1,000，net 不变
  分红不入账 → trading 掉 1,000，fx 被算成 +1,000
  报表显示：汇率损益 +1,000  ← 真正的原因（分红）消失了
  归因恒等式：仍然闭合 ✅
```

第五项 `CORPORATE_ACTION` 的严重度排在持仓差异与现金差异**之前**，因为它是根因：
分红没入账会同时造成现金差异和持仓差异，先报现金差异等于让运维去修症状。

**证据五：拆股只改数量，绝不改金额**

```
拆股前：qty=50, avg_cost=180, buy_at_decision=9,000
2:1 拆股后：qty=100, avg_cost=90, buy_at_decision=9,000  ← 不变
若改 buy_at_decision：凭空产生 +9,000 收益，且没有任何一笔成交能解释它
```

**证据六：幂等去重不能顺手污染派生字段**

这条是本批修掉的第二个真实 bug，症状很隐蔽：

```
交易所重复回报同一笔入金 → 现金只加一次（去重生效）
                           net_deposits_base 却加了两次（派生字段无条件累加）
结果：net_pnl 凭空 -100,005，差额全部被 fx 残差吞掉，closes 依然 True
```

`Ledger` 现在提供 `was_written(entry)`，所有派生字段累加都挂在它后面：
「这笔分录是本次新写入的吗？不是就一分钱都不许动。」这条也顺手证明了
**恒等式闭合本身证明不了什么** —— 它能被残差项吸收掉任何错误。

### 已知限制

1. **协方差估计只解决「给定假设怎么摊」，不解决「假设会不会变」。** 模型年龄 > 30 天
   会判不可信，但 30 天是拍的阈值，没有依据说 29 天就一定安全。真正的做法是
   滚动重估 + 对 ρ 变化做敏感性，本批没做。
2. **只用简单收益率 + EWMA，没有做因子模型。** 794 只 A 股全上会撞上
   「参数个数 O(n²) 而观测数只有 O(T)」的墙：n=794 需要 315,271 个参数。
   实际只能压缩到几十只或改用因子结构，这块属于研究层，不在本批范围。
3. **公司行动只覆盖分红 / 拆股 / 融资利息三项。** 权证行权、并购换股、供股、
   借券费都没纳入。券商声明里出现未知类型时，对账会报「未知公司行动」而不是默认没问题，
   但那也只是报出来，不会自动处理。
4. **分红税按账单金额倒推，不做税务规则计算。** `gross_amount` 与 `withheld_tax`
   都来自券商账单的拆分；不同市场（美股 30%/爱尔兰 15%/港股不同）的预扣逻辑没有建模。
5. **灰度只到版本级，参数级灰度仍未做。** 这条从 B6 原样留到现在，
   `research_inbox` 里的「参数建议」接受之后是落成新版本再走灰度，不能只灰度一个参数。
6. **`CanaryRouter` 仍是纯内存。** 重启后路由表靠审计日志重建，而重建函数依然没实现。
   页面上能看到灰度状态，但那份状态活不过一次进程重启。
7. **页面探针是 DOM 桩，不是真浏览器。** `page_probe.js` 用极小的 DOM 子集验证
   「渲染出来的数字等于后端 JSON」，能抓数字漂移和漏字段，抓不到 CSS 布局问题。
   布局另用 headless Chrome 截图人工核对（1440 / 500 两个宽度）。
   Chrome headless 的窗口宽度下限是 500px，390px 真机宽度没法用命令行验证，
   只能靠窄屏规则是「窄屏竖排 + `minmax(0,1fr)`」这一点来保证不横向溢出。

### B8 DoD 达成证据

**证据一：整条链路第一次被同一次调用串起来**

```
2026-09-30: 信号 2 条 / 意图 2 条 / 目标 3 个 / 成交 2 笔 / 限额重算 2
            净值 100000 → 99997.1996（手续费 0.8004 + 滑点 2.0000）
```

在此之前每层单独测都过，但"整条链路是对的"这个结论一直是靠分测拼出来的印象。
现在它是一次真实调用的结果，而且成本能在净值上被看见 —— 如果是 0，
那说明 `apply_fill` 根本没跑到，而不是"没有成本"。

**证据二：风控的 `REDUCE_REQUIRED` 以前没人接**

`RiskEngine` 对大单返回 `REDUCE_REQUIRED` 并给出 `cap_notional`，注释写着
"要求上游按 cap 用原意图重算，风控不代改单量" —— 但**上游根本没有人在做这件事**。
接上运行时之后立刻暴露：

```
策略想买 10,000（占 NAV 10%）
  风控：> 单笔上限 2%，返回 cap 2000
  运行时（新）：target.capped(2000) → 重新 prepare/submit → 成交
  运行时（旧）：记一笔 "被拒"，仓位永远建不起来，报告显示"风控正常工作"
```

只重算一次，不循环：允许循环等于让策略用"被拒 → 缩小 → 再拒"的方式试探风控边界。

**证据三：导入不等于能下单（这条以前是漏的）**

`StrategyInstance.tradable` 只看 `run_state`，**不看 `stage`**。
于是 `policies()` —— 喂给资金分配器的候选池 —— 会把一个刚导入的 RESEARCH 策略
也带进去。`effective_quota_pct()` 的注释写着"RESEARCH 不真下单，但保留配额供模拟"，
而代码里没有这个判断，那句话只活在注释里。

修法是给 `policies()` 加 stage 过滤（只收 PAPER / LIVE），并同步改了 B3 里
一条把这两件事混在一起的旧断言。边界同时钉住：PAPER 暂停后不给配额，
但 `include_paused=True` 时仍可见 —— 修得过头也没意义。

**证据四：策略包必须零 import**

第一版契约要求策略返回 `SignalOut`，结果是**每个包都必须 import `quantos_core`**，
而 AST 白名单又不允许 —— 体检当场把这个设计矛盾顶了出来。
于是改成：推荐返回 dict（零 import），`SignalOut` 作为可选写法（唯一放行的模块是
`strategy_api`，纯数据契约）。附带好处是：dict 形态跨语言、跨仓库、跨进程都能用，
将来接 Python 以外的策略不用重写契约。

**证据五：干跑是导入的一部分，不是可选项**

一个"导入成功但跑不起来"的策略最危险：它出现在策略列表里，看起来已经就位。
所以 `load_pack(..., dry_frame=...)` 会真调一次 `compute()`：

| 干跑返回 | 结论 |
|---|---|
| `None` | 拒 —— 分不清"没信号"和"忘了 return" |
| 字符串 / dict | 拒 —— 必须返回信号序列 |
| 未知键的 dict | 拒 —— 拼错的 `wieght` 会静默变成 0 权重，看起来像"策略看空" |
| 权重 > ±1 | 拒 —— 超过部分等于策略自己想加杠杆 |
| 没有 `reason` | 拒 —— 事后无法回答"为什么做这笔交易" |
| 抛异常 | 拒，且消息带策略 id |

### 上屏／可用性

新增一条命令，把"能不能导入"变成一个可执行的判定：

### 本次修掉的问题

### 已知限制

1. **AST 体检是门槛，不是沙箱。** 挡得住无意的越界，挡不住精心构造的逃逸。
   真正的隔离（独立进程 / 无网络 / 只读 FS / 资源限额）属于部署层 B10，本批不做也不假装做了。
2. **运行时是单进程的。** `EngineRiskClient` 是 `RiskEngine` 的进程内适配器，

3. **`PaperBroker` 不是撮合模拟。** 它按"决策价 ± 固定滑点 + 固定费率"立刻全额成交，

4. **`rebalance_days` 只被记录，还没有调度器读它。** 真正的按周期调度需要

5. **没有回测引擎。** `strategy_pack` 只验证"能算、算得对"，不回答"这个策略赚不赚钱"。
   样本外回测仍是 `research/` 里手工做的事，报告 id 由人提供给 `promote()`。
6. **策略级盈亏仍不是精确值。** 成交已经带策略归属（C3 断言归属数量 == 成交数量），
   但成本分摊与已实现盈亏还是账本层按比例算的（R-D05 遗留）。

### B9 DoD 达成证据

**证据一：日历是「数据即事实」，不是手抄节假日**

A 股每年 11 月才公布次年休市安排。手抄一份表，抄错一天全错，而且**错了没人会发现**。
所以本批反过来做：从真实行情的日期反推哪些工作日没交易。

```
510300 日线 2018-07-24 ~ 2026-10-23，1999 个交易日
推出休市日 155 个   各年：2018:7 2019:17 2020:19 2021:18 2022:19
                          2023:18 2024:20 2025:18 2026:19
```

对照 2026 年那 19 天：`01-01/02`（元旦）、`02-16~02-23`（春节）、`04-06`（清明）、
`05-01/04/05`（劳动）、`06-19`（端午）、`09-25`（中秋）、`10-01/02/05/06/07`（国庆）。
一条不差 —— 因为这些日子**不是被写进来的，是被数据说出来的**。

**证据二：规则日历的误差是可量化的，方向也是确定的**

```
规则日历（只认周末）在 2154 个工作日里错判 155 天，年均 17.2 天
  漏判（把交易日当休市）  0 天   ← A 股没有周末补班交易，这一向必然为 0
  多算（把休市日当交易日）155 天 ← 全部误差都在这一向
```

方向很重要：多算的后果是那一拍拿不到行情 → 被 fail-closed 拦下 → 晚一天调仓。
**如果反向有误差（漏判），后果是整整一次调仓被静默跳过，而且没人会发现。**
所以 `audit_rules_against_data()` 把两个方向分开报，并且规定

> `silent_skips > 0` 的日历一律不许用。

同一份日历再拿 **60 只个股**去交叉验证（不是同一数据源，才不是同义反复）：双向 0 差异。

**证据三：漏跑不漂移 —— 这是本批的核心**

```
anchor = 3-02，每 5 个交易日；跑到 3-02 之后挂了，4-01 才恢复

从锚点算（正确）：下一次到期 = 4-06   ← 落在锚点相位上
从上次运行算（错误）：下一次到期 = 4-01
再推 10 次：两者仍然错开，漂移不会自愈
```

`next = last_run + N` 看起来自然，实际上**一次晚跑就等于永久偏移**。
一年之后回测的"20 日"和实盘的"20 日"会错开十几个交易日，而两边都觉得自己是对的。
所以周期一律 `anchor + k × N`，`anchor` 一旦落盘就不许静默改（改相位要显式 `rebase`）。

**证据四：「跑没跑成」有三种状态，而且必须分开**

落盘是一个**有洞**的流程：进程可能在下单之后、落盘之前被 kill。
这时"重跑"是重复下单，"不重跑"是漏一次调仓 —— 两个都不对。

```
claim(数据日) → 落盘 → 执行 → complete → 落盘

runner 抛 PreflightAbort（明确知道自己还没碰任何有副作用的东西）
   → FAILED，清 claim，下一拍直接重试        ← 确定没跑
runner 抛别的异常
   → FAILED_IN_DOUBT，**保留 claim**，下一拍 REFUSED_IN_DOUBT
   → 必须人工 resolve(cleared / assumed_done) ← 不知道跑没跑
```

这和 B5 错误分类里的 `ambiguous`、OMS 的 `needs_reconciliation` 是同一条原则：
**把不确定变成可发现的、需要人签字的错误，而不是猜一个方向然后祈祷。**
`resolve()` 也守同一条线：actor 必须以 `human:` 开头，理由至少 6 个字 ——
这一条决定的正是"那天到底有没有下单"。

**证据五：收盘前算的不是 close**

```
09:00 → 上一交易日     14:59 → 上一交易日
15:00 → 上一交易日（还没过结算延迟）
15:30 → 当日
周六 10:00 → 周五      休市日 16:00 → 上一个交易日
```

回测里"用当日收盘价决定、次日开盘成交"里的 close 是 15:00 的。
实盘如果在 14:00 跑，拿到的那个数字**也叫 close**，两边看起来完全一样，
差的却是真金白银。`signal_day()` 因此规定：当日没收盘 + 结算延迟之前，一律退回上一个交易日。

**证据六：真实 A 股连跑两拍**

```
2026-06-01（第 0 拍）  3 笔成交，净值 100000 → 99995.7994（手续费+滑点确实扣了）
2026-06-30（第 20 个交易日，第 1 拍）到点执行，基于第一拍持仓算差额
同一数据日再 tick → skipped_already_ran，成交笔数不变
```

另外 `build_frame_for_day()` **只取 ≤ 数据日的 bar**。日线文件里带着未来所有日期，
截不截完全靠调用方自觉 —— 这是整条链上最容易漏掉的前视偏差防线，所以给它一条断言。

### 上屏（T-904）

新增只读端点 `/api/ops/schedule` 与「策略排期」卡片。三条硬规矩：

1. **`status_snapshot()` 是纯函数，运维面拿不到 `tick()`** ——
   一个只读看板不该握着"能推进一拍"的对象（那等于给它一个下单按钮）；
2. **缺日历 / 有 in_doubt / 连续失败都显示红**，不挂绿灯。两个故障注入
   （`--fault sched-in-doubt` / `--fault sched-stale-calendar`）证明这张卡**真的会红** ——
   只会亮绿灯的看板等于没有看板；
3. **in_doubt 时"上次结论"让位给当前状态**。两者同时显示会互相打架
   （一个写"已跑"、一个是红的），而当前状态更重要。

### 本次修掉的问题

- **`status` 会顺手登记排期**。只读命令改状态是绝对不能有的行为，改成"盘上没有就如实说没有"。
- **命令行默认锚点覆盖盘上锚点**。跨年那天相位会自己跳一次，而 `last_run_day` 还留着，
  两边对不上。改成**盘上锚点优先**，显式给不同 `--anchor` 又没 `--rebase` 时直接报错。
- **`build_from_observed` 端点误判**。若不限定区间，区间外的工作日会被算成休市日 ——
  这是最容易造出来的假节假日，已加断言钉住。
- **`first_day=inside and min(inside) or lo`** 这种写法在集合为空时会静默取 `lo`，
  把"没有数据"变成"从 lo 开始"。改成直接 `min(inside)`（前面已经保证非空）。
- **排期异常以 traceback 形式抛给用户**。配置错是用法问题不是崩溃，改成一行说明 + 退出码 2。

### 已知限制

1. **账本仍是进程内的。** `Ledger` 没有落盘能力，所以独立进程跑两次 = 第二次从空仓开始建仓，
   目标权重全部重算一遍。`tick` 会在输出里明说这件事，`--repeat` 用于在同一进程内连推多拍。
   **真实部署必须先解决账本持久化**（B10）。→ **已在 B10 解决**，见第 12 章。
2. **日历只负责到「最后一个有数据的交易日」。** 之后的日子调度器拒绝运行而不是按规则猜。
   这意味着**必须每天更新行情**，否则系统会停在上次数据那一天并明确报错
   （停住是安全的，猜一天才是危险的）。
3. **没有节假日表。** 11-12 月的休市安排要等行情补上才能推出来。若将来要提前排期，
   需要一份可校验的节假日配置 + 与数据的双向对账。
4. **调度器不自己定时。** `tick()` 的语义是"现在该干什么就干什么"，定时由外部
   （systemd timer / cron / while 循环）负责。进程编排属部署层 B10。
5. **只支持单一场所的单一日历。** Crypto 24/7 的排期还没接进来 ——
   `scheduler.py` 的多 lane 已经有了，但 `RebalanceSpec` 目前按 A 股交易日历判定。
6. **`resolve` 是本地函数调用，没有审计落库。** 结论写回了排期状态文件，但没有进 `AuditLog`；
   真钱阶段这条要补（谁在什么时候判定"那天没下单"必须有独立记录）。

## 12. B10 · 账本落盘与进程编排（✅ 代码完成 2026-10-27）

### 12.1 为什么是这一批

B9 让策略「到点会自己跑」，同一次运行里就暴露了下一道墙 —— `AshareRunner`
的 docstring 自己写着「独立进程跑 = 新账本 = 从空仓开始」。这不是"差不多能用"：
第二拍的「目标 - 当前」会把已有持仓当成 0，把已经买过的再买一遍。

更隐蔽的是**幂等索引也跟着没了**。`Ledger._refs` / `_by_key` 活在内存里，
进程重启后交易所的重复成交回报会被当成新成交再记一次 —— 现金和持仓一起翻倍，
账面自洽、对账不平，而任何单看账本的检查都发现不了。

### 12.4 这一批修掉的真 bug

**`apply_split` 不是幂等的。** 它先把 `pos.qty` 乘上比例，再 `post()` 去重 ——
去重只挡住了分录，没挡住数量。重放同一条拆股通知（或重启后重放公司行动）：

```
拆股前 100 股 → 2:1 拆股 200 股 → 同一 ref 再来一次 → 400 股
账本里始终只有 1 条 SPLIT 分录，分录数、金额、归因恒等式全部正常。
```

这类错不会在任何一致性检查里露头，只能靠「去重门放在改状态之前」这一条架构约束。
已在 `apply_split` 里加早退，并用 H4 断言钉住「门在改数量之前」的代码顺序。

顺带修掉一个会安静吞掉漏拍的退出码问题：`cmd_tick` 原来只在 `in_doubt` 时返回 1，
**整拍被拒（日历未校准）返回 0**。cron 会认为"今天正常"，而实际是今天该调仓却没调。
现在 `refused` / `failed` 一律返回 2。

### 12.5 已知限制

1. **快照写全量分录，没有 compaction。** 分录到十万条级别时每次保存都会变慢
   （现在是每拍一次，几万条以内没问题）。
2. **`.bak` 与主文件同盘。** 防进程崩溃与写坏，防不了磁盘损坏。
3. **没有跨进程写锁保护账本文件本身。** 互斥靠 `quantos_tick.py` 的
   `AccountGatewayLock`；直接手敲 `quantos_schedule.py tick --execute` 会绕过它。
4. **tick 仍用进程内风控引擎**（`EngineRiskClient`）。独立风控服务在跑，
   但没接进下单链路 —— `quantos_up.py --status` 会明说这一点，不假装接通了。
5. **风控状态有两个文件**：`ashare_risk.json`（进程内引擎）与
   `risk_service.json`（独立服务）。接入后应合并成一个真源。
6. **日历覆盖区间 = 数据覆盖区间。** 数据没更新到今天就拒绝运行（见 11.5 第 2 条）——
   所以 cron 每天早上会以退出码 2 提醒"该补数据了"，这是设计而不是故障。
