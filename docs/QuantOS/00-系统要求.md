## 0. 定位与成功标准

**R-G01 系统定位**：一个人可以管理的、多策略、多市场、**自有资金**量化交易系统。不做资管、不做对外募资。

**R-G02 使用体验**：投入一笔资金 → 设定投资范围与风险预算 → 选择要跑的策略 → 之后 7×24 自动管理 Crypto，并在股票交易时段自动交易股票。日常不需要逐笔确认，但随时可以查到：

| 用户随时要能回答的问题 | 落到哪个服务 |
|---|---|
| 每个策略用了多少资金、赚了多少钱 | Capital Allocator + Portfolio Ledger |
| 股/币分别持有什么仓位、风险多大 | Portfolio Ledger + Risk Engine |
| 系统为什么做这笔交易、执行得怎么样 | Strategy Engine 信号 + OMS/EMS 回报 |
| 要不要自动减仓、停策略、调配置 | Risk Engine + 控制台操作 |
| 系统有没有异常、异常后有没有正确停止新增风险 | Operations Center + Risk Engine |

**R-G03 验收总原则**：以「真实资金能否安全运行」作为每阶段验收标准，不以页面完成数量衡量。**能安全停下** 优先于 **能赚钱**。

**R-G04 非目标（本版明确不做）**：高频做市、超低延迟套利、对外募资/受托资管、浏览器系统推送、多租户账号体系。

## 1. 顶层架构（R-A）

**R-A01 两个平面**：系统必须拆成「研究控制平面」与「生产交易平面」。

| 平面 | 内容 | 部署位置 |
|---|---|---|
| 研究控制平面 | 行情历史库、回测与参数优化、AI 策略研究、版本发布审批 | Mac mini（研究节点） |
| 生产交易平面 | 实时行情与策略、组合资金分配、订单执行与风控、对账监控恢复 | Linux x86 云服务器 |
| 生产交易网关 | 股票 Gateway（IBKR / Alpaca）、Crypto Gateway（Bybit / OKX 等） | 生产节点 |
| Web 管理平台 | 资产监控、策略管理、回测分析、风控设置、审计 | 独立入口，经 Cloudflare Access 类身份认证 |

**R-A02 故障隔离（硬性）**：Web 控制台宕机**不得**影响正在运行的策略、订单管理与风控；策略进程崩溃**不得**直接导致风控进程失效。风控必须是独立进程/服务。

**R-A03 事件驱动主链路**：`实时行情 → 策略引擎 → 目标持仓 → 组合资金管理 → 交易前风控 → 订单管理 → 记录原因与告警 → 执行管理 → Broker/Exchange → 成交与订单回报 → 仓位账本/资金账本 → 实时风险计算`，旁路 `独立账户对账`，对账不一致 → `暂停相关交易/人工排查`。

**R-A04 单活执行**：订单执行采用单活（single-active）架构，两个节点同时执行同一订单必须不可能。沿用现有 `core/trading_lock.py` 的 flock 单实例锁思路，扩展到「账户 × 网关」维度。

**R-A05 生产入口不直暴公网**：交易网关不直接暴露公网；Web 入口经身份认证；敏感操作需要二次确认 + 权限控制 + 审计日志。

## 2. 三个不可协商的设计决定（R-A）

**R-A06 策略不能直接下单**。策略只能发出「交易意图」，最终交易量由资金管理与风控决定。意图结构：

```json
{
  "strategy_id": "crypto_trend_v1",
  "symbol": "BTC/USDT",
  "venue": "OKX",
  "target_weight": 0.15,
  "confidence": 0.82,
  "reason": "trend_following"
}
```

`confidence` 只是策略自身指标，**不代表真实盈利概率**，不得进入仓位计算公式。

**R-A07 多策略由统一组合管理器协调**。趋势策略想买 0.2 BTC、均值回归想卖 0.1 BTC 时，不允许各自盲目执行：先汇总目标敞口 → 组合管理器算净差额 → 再检查已有订单/当前持仓/可用资金 → 才决定实际下单量，避免重复下单。

**R-A08 订单管理必须支持故障恢复**。订单状态至少覆盖：已提交、交易所已接受、部分成交、完全成交、撤单中、已撤销、**状态未知**。请求超时必须**先查交易所状态**，用稳定客户端订单 ID 防重复执行，**严禁超时即假定失败并重试**。

## 3. 资金管理 Capital Allocator（R-C）

**R-C01 不把策略当独立炒股机器人**。设中央资金管理系统，决定每个策略能用多少资金、承担多少风险、策略间如何再分配。

**R-C02 组合示例（仅演示分配能力，非投资建议）**：NAV $100,000 → 股票策略池 $50,000 (50%) / Crypto 策略池 $30,000 (30%) / 现金及风险缓冲 $20,000 (20%)。
必须在产品口径上说明：真实资金分存于券商、交易所、现金账户，**不存在可无条件跨平台调拨的统一资金池**。

**R-C03 三种分配模式**：固定配额 / 波动率目标 / 风险预算分配（风险贡献+相关性+总体敞口）。**第一版实现「固定配额 + 波动率约束」**，风险平价与动态组合优化后置。

**R-C04 资金 ≠ 风险**。必须同时计算：名义持仓、杠杆后敞口、资产相关性、市场方向、各策略风险贡献。两个策略各用 $20,000 且都做 BTC 多头时，必须识别为风险高度集中。

## 4. 风控 Risk Engine（R-K）

**R-K01 独立于策略运行的核心服务**。三道防线：

| 层级 | 检查内容 | 触发动作 |
|---|---|---|
| 订单级 | 单笔金额、价格偏离、流动性、重复订单、最小交易单位 | 拒绝订单 |
| 策略级 | 策略亏损、异常换手、持仓限制、信号过期 | 暂停策略新增仓位 |
| 基金级 | 总账户回撤、组合敞口、交易所异常、资金不一致 | 全局禁止新增风险 |

**R-K02 初始风险配置（演示值，真实阈值需按频率/流动性/滑点/压力测试确定）**：

```yaml
risk_policy:
  max_order_notional_pct: 2.0
  max_strategy_allocation_pct: 20.0
  daily_loss_pause_pct: 1.0
  drawdown_pause_pct: 5.0

  stale_market_data_action: block_orders
  position_mismatch_action: block_orders
  unknown_order_status_action: reconcile

  allow_leverage: false
  withdrawal_api_permission: false
```

**R-K03 三级交易权限**：`NORMAL` 正常交易 / `REDUCE_ONLY` 仅允许降低风险 / `HALTED` 停止自动交易。

**R-K04 HALTED 不等于立即市价清仓**。市场断连、流动性不足、订单状态未知时盲目清仓可能造成更大损失。必须按异常类型选择：冻结新增订单 / 撤销未成交委托 / 受控减仓。

**R-K05 风控状态必须落盘**，重启不失忆（沿用 `state/risk_state.json` 机制）。风控拒绝必须留下可解释原因。

## 5. 策略工厂（R-S）

**R-S01 生命周期**：`Research → Backtest → Paper → Live`，每阶段有准入门槛。

**R-S02 每个策略版本必须绑定**：参数、代码提交 ID、数据版本、成本模型、回测报告、上线记录。

**R-S03 进入实盘的准入条件（全部满足）**：通过样本外回测、计入真实手续费与滑点、模拟盘交易状态正确、异常订单处理测试通过、**人工授权上线**。

**R-S04 AI 边界**：AI 可辅助生成策略、提优化建议，**不得**自行修改生产策略并直接上线实盘。

**R-S05 第一批策略池**：

| 市场 | 策略 | 频率 |
|---|---|---|
| 股票 | ETF 动量轮动 | 日 / 周 |
| 股票 | 趋势突破 | 日线 |
| Crypto | 趋势跟踪 | 1h / 4h |
| Crypto | 均值回归 | 15m / 1h |
| Crypto（后期） | 资金费率中性 | 按结算与对冲条件 |

第一阶段**不做**高频做市、超低延迟套利。

**R-S06 研究=生产同一套计算逻辑**，通过事件回放测试防止回测信号与实盘信号偏差。

## 6. 技术选型（R-M / R-A）

| 模块 | 选型 |
|---|---|
| 前端控制台 | Next.js + TypeScript |
| 服务端 API | FastAPI |
| 研究与回测 | LEAN + Python |
| 实盘策略运行 | Python 事件驱动运行时 |
| 组合与风险 | 独立 Python 服务 |
| 订单执行 | 自建 OMS/EMS + 适配器 |
| Crypto 接口 | CCXT + 交易所原生 WebSocket |
| 股票接口 | IBKR / Alpaca |
| 事件队列 | Redis Streams |
| 持久化 | PostgreSQL + TimescaleDB |
| 历史批量数据 | Parquet + DuckDB |
| 图表 | TradingView Lightweight Charts + ECharts |
| 监控 | Prometheus + Grafana + Alertmanager |

**R-M01 CCXT 不假设功能一致**：不同交易所的订单查询与状态支持有差异，生产 OMS 不能假设能力对等，需按交易所声明能力矩阵。

**R-M02 现有技术债过渡说明**：本仓库当前实现为 Python 单体 + 老虎券商 + yfinance/Alpaca 行情 + Apache 调度。上述选型是目标态，迁移以「不打断已验证的执行链路」为前提分批替换（见 `03-推进路线图.md`）。

## 7. 部署（R-A / R-O）

**R-A09 部署分工**：
- **Mac mini = 研究节点**：历史数据处理、回测任务、AI 辅助研究、策略开发、非关键服务。
- **Linux 云服务器 = 生产交易节点**：策略、资金管理、风控、执行服务独立运行；持久化事件、自动重连、备份与故障恢复；订单执行单活。
- **Web 入口**：Cloudflare Access 类身份认证。

**R-A10 两条已核实的外部限制（必须在产品口径中保留，不得承诺规避）**：
1. **IBKR IB Gateway 不是完全免维护的无人值守接口**：官方文档说明需要图形化认证，且通常需周期性重新认证。**不能承诺股票系统永久无人值守。**
2. **LEAN + IBKR 目前不支持 Apple Silicon ARM Docker 镜像本地实盘部署**。因此该组合不放在 Mac mini 承担生产交易，改用 x86 Linux 节点或其他受支持方式。

## 8. 数据与账本（R-D）

**R-D01 独立 Portfolio Ledger**，而不是读交易所余额直接显示。基金级净值统一折算到一个计价货币，同时保留原币种记录。

**R-D02 最小数据模型**：

| 对象 | 作用 |
|---|---|
| accounts | 券商与交易所账户 |
| instruments | 股票、ETF、现货、合约标准化定义 |
| strategies | 策略配置、版本、运行状态 |
| signals | 策略信号及触发依据 |
| portfolio_targets | 策略目标持仓 |
| orders / fills | 委托与实际成交 |
| positions | 账户真实持仓及策略归属 |
| ledger_entries | 现金、费用、分红、资金费率记账 |
| risk_events | 风控命中、熔断、恢复 |
| audit_logs | 人工与自动操作记录 |

**R-D03 收益归因可拆分**：策略交易收益、汇率收益、手续费、滑点、资金费率必须分别可见；**入金/出金不得扭曲收益率**。

**R-D04 每日对账**：系统现金、持仓、未成交订单、成交记录必须与券商/交易所一致。发现差异 → 相关账户**禁止继续增加风险**，直到校验完成。

**R-D05 仓位归属**：同一标的可能被多个策略持有，`positions` 必须记录策略归属与数量，否则无法按策略算盈亏。

## 9. 可视化与控制台（R-O）

**R-O01 首页 = 基金经理交易台**，不是普通 K 线软件。必须呈现：基金净资产、累计与当日收益、当前风险敞口（名义/NAV）、当前回撤、策略运行情况（运行/暂停数）、各策略盈亏与状态。

**R-O02 Operations Center（交易运维中心）必须存在**——这是多数个人量化系统缺失的部分。必须同时呈现：行情延迟、WebSocket 连接、策略心跳、最近一次信号、订单执行延迟、失败订单、待对账记录、账户异常、熔断状态。

**R-O03 策略实例像 K8s 工作负载一样管理**：查看版本、暂停、恢复、灰度发布、回滚、审计记录。

**R-O04 演示与真实边界**：原型阶段的数字必须明确标注为虚构/演示数据，不得暗示为真实回测表现或收益预测。部署到公网的页面不得预填真实隐私数据（真实金额、真实持仓、真实健康数据）。

**R-O05 当前已交付原型**：`quantos/index.html`（资料库在线页 + 云端审计台账）。定位为**概念原型**，接生产平面后替换数据源。

## 10. 开发顺序与阶段验收（R-G）

| 阶段 | 建设内容 | 完成标准 |
|---|---|---|
| Phase 1 | 行情、数据模型、策略、回测 | 回测可复现；数据与成本模型可验证 |
| Phase 2 | 账户、账本、组合分配、OMS、模拟盘 | 能完整模拟「订单 → 成交 → 对账」 |
| Phase 3 | 实盘网关、风控、监控、故障恢复 | 断网、超时、重复事件、服务重启测试全部通过 |
| Phase 4 | 小规模实盘、绩效归因 | 自动运行并持续与真实账户对账 |
| Phase 5 | 多市场、多策略、AI 研究与动态组合 | 多策略不重复占用资金；整体风险可控 |

**R-G05 上线前必须做故障注入**：模拟行情停止、网络请求超时、交易所重复回报、部分成交、服务器重启、数据库不可用。**只有系统能正确恢复或安全停止交易，才可进入下一阶段。**

**R-G06 外部资金边界**：若未来引入外部投资者资金，必须另设投资者账本、申赎、净值核算与合规流程；**不得**把个人自营系统直接当受托资产管理系统使用。

## 11. 第一版范围（R-G）

| 项 | 取值 |
|---|---|
| 项目定位 | 个人自营量化基金操作系统 |
| 第一批市场 | 美股 ETF + Crypto 现货 |
| 股票网关 | 优先评估 IBKR（现有老虎券商作为过渡与对照） |
| Crypto 网关 | 选择一个账户可用、合规的交易所 |
| 策略数量 | 3 个正式 + 1 个实验 |
| 策略周期 | 15m 至日线 |
| 交易模式 | 先模拟，验证后才开小额实盘 |
| 语言 | Python + TypeScript |
| 部署 | 云端执行 + Mac mini 研究 |

**R-G07 设计基调**：前端像专业基金管理终端，后台像交易系统，工程可靠性参照生产级 SRE 标准。

**R-G08 下一层设计焦点**：`Strategy Engine → Capital Allocator → Risk Engine → OMS/EMS → Portfolio Ledger` 五个关键服务的边界与数据契约。这条主链路设计正确，后续接新策略/市场/交易所/更多 AI 研究能力都不需要推翻底层。→ 见 `02-服务数据契约.md`。
