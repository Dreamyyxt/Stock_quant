## 这一批解决的是哪道墙

B9 让策略"会自己跑了"，但跑出来的持仓只活在内存里：

- 进程一退，持仓归零；
- 第二拍调仓时，现有持仓被当成 0，**每拍都从空仓重新建**；
- 累计盈亏永远进不了预算口径（预算固定用初始资金）。

这三件事都不是"少存一个文件"，而是"账本根本不存在"。所以 B10 不是加缓存，
是把账本变成一份可恢复的状态。

## 四条设计结论

1. **整份快照，不重放分录。** `buy_at_decision` / `slippage` / `attr_qty` 这些派生字段
   不是分录的函数 —— 改持仓的是入参（决策价、归属比例），这些不进分录。
   只存分录再"重放"出来，等于伪造一批不同的持仓。
2. **恢复时必须重建幂等索引**（`_refs` / `_by_key` / `_seq`）。只把数字读回来、
   不重建去重表，文件看着一模一样，但**防重放能力为零** —— 比不落盘更危险，
   因为它看起来是好的。
3. **坏档绝不静默当空账本。** `load()` 返回显式状态，`must_load()` 坏档直接抛。
   拿空账本顶上，会让一次数据损坏被读成"账户清零"，然后下一拍照着空仓去建仓。
4. **退出码就是报警线。** 0 正常 / 1 in_doubt / 2 拒绝运行或失败 / 3 锁被占。
   "拒绝运行返回 0" 是假绿灯 —— cron 会当成"今天正常跑过了"。

## 修掉的真 bug

`apply_split` 原来是「先改数量 → 再 `post()` 去重」：

```
100 股 --split 2:1--> 200 股
同一 ref 再放一次 --> 400 股
```

而账号里只有 **1 条** SPLIT 分录，所以六项归因、现金恒等式、NAV 全都正常 ——
任何断言都抓不到。改成去重门前置后：`200 → 200`，`attr_qty` 也只乘一次，
并加了 H4 顺序断言（断言的是"门的顺序"，不是"结果对不对"）。

## 硬证据

**两进程两拍（真实 A 股行情，`2026-09-30`）**

| | 进程 1 | 进程 2 |
|---|---|---|
| `ledger_status` | `created` | `ok` |
| 起始持仓 | 空仓 | **正是进程 1 留下的那 4 只** |
| 本拍成交 | 4 笔 | 只补 1 笔差额 |
| 预算 NAV | 100000（初始） | **100188.0869（账本真实 NAV）** |

进程 2 只补 1 笔，说明它读到了进程 1 的持仓；NAV 不再是固定 10 万，
说明上一拍的盈亏真的进了预算。

**上屏会真的变红**：`--fault ledger-corrupt` 把文件截一半，卡片显示
「账本损坏 / 0 条 / 拒绝运行」+ 红色警示条，没有被伪装成"空仓"正常态。

## 已知限制（写进 03-推进路线图 12.5）

- 账本单文件全量重写，分录多了会变慢（还没到量）。
- `.bak` 只留一份，连续两次坏档就没了。
- tick 仍用**进程内**风控引擎，没走风控服务的 socket。
- 执行网关未接入（`form="absent"`），成交走 `PaperBroker`。
- 无进程守护 / 崩溃重启。
- `quantos_up` 只看 pid 与探针，没有真正的健康检查协议。
